## 1. Verdict + Proven Scope + 最大未验证项

### Verdict: `EVIDENCE_REQUIRED` (partial baseline established)

内核层（CordisContext / EventBus / PluginHandle）已建立可复现微基准。完整桌面 shell 的启动时间、UI 帧率、稳态 CPU/内存、交互延迟**未测量**——因运行 BetterDesktop 会接管用户桌面（隐藏任务栏、自绘桌面、注册 AppBar），当前无 headless 模式可安全绕过。

### Proven Scope
- 内核 DI（Provide/Get）、插件注册/加载/卸载、EventBus 五种分发模式的单次操作延迟
- 内核内存泄漏检测（100 context × 20 plugin create/dispose 循环）
- 功能测试基线（335 tests, 334 pass / 1 pre-existing failure in shell-convert）
- 静态热点扫描（UI 线程阻塞、同步等待、轮询定时器、每帧回调）

### 最大未验证项
**完整 shell 启动 wall-time（CLR init → 插件加载 → 首帧）**。Bootstrap.Build() 硬编码 20+ 插件顺序加载，每个插件的 LoadAsync 执行真实 WPF 窗口创建与 IO。内核调度本身仅占 ~63 µs（20 插件），真实启动开销完全在插件 LoadAsync 内部，需受控环境测量。

#### C1: Provide<T> 的 NotifyDependents O(N) 遍历开销
- **证据**: `provide-get-with-20-plugins` (0.0177 ms/op) 比 `provide-get-no-plugins` (0.0005 ms/op) 慢 **34.4 倍**
- **机制**: `CordisContext.Provide<T>` line 71 调用 `NotifyDependents(type)`，遍历 `_plugins` 列表对每个插件调用 `OnServiceChanged(serviceType)`，后者检查 `_plugin.Inject.Contains(serviceType)`
- **影响范围**: Bootstrap 中有 10+ 次 Provide，每次触发 20 插件遍历。但单次仅 17.7 µs，100 次 Provide 也仅 1.77 ms — **对启动时间影响有限**
- **状态**: `EVIDENCE_REQUIRED` — 需 diagnose 确认在真实插件 LoadAsync 中频繁 Provide 时的累积影响
- **字面状态转移**: 每次 Provide → `_services[type] = service` → `NotifyDependents(type)` → 对每个 plugin: `if (!_plugin.Inject.Contains(serviceType)) return; else RestartSerializedAsync()`

#### C2: EventBus.Snapshot 每次 emit 分配 List
- **证据**: 静态源码 `EventBus.cs:137-143` — `Snapshot()` 在 `lock(_gate)` 中执行 `list.ToList()`，每次 Emit/Parallel/Serial/Bail/Waterfall 都调用
- **测量**: `eventbus-emit-1-handler` median 12.3 µs，其中包含 List 分配 + Task.WhenAll 开销
- **影响**: 高频事件 (如鼠标移动、窗口位置变化) 可能产生大量 Gen0 分配
- **状态**: `EVIDENCE_REQUIRED` — 需 diagnose 用 allocation profiler 确认事件频率与 GC 压力

#### C3: eventbus-parallel-10-handlers 高方差
- **证据**: stddev/median = 71% (0.034/0.048 ms)，样本1 0.105 ms vs 样本3 0.044 ms
- **机制**: `Task.WhenAll` 等待 10 个并发 Task，线程池调度延迟导致尾延迟
- **状态**: `EVIDENCE_REQUIRED` — 需 diagnose 确认是否在 UI 线程调用 ParallelAsync 导致帧卡顿

### 7.2 静态分析候选 (`ASSUMPTION`)

#### C4: UI 线程阻塞 — Dispatcher.Invoke 同步调用
- **位置**:
  - `shell-desktop/Windows/DesktopWindow.cs:213` — `Dispatcher.Invoke(() => ...)` (桌面菜单委托)
  - `shell-quick-note/QuickNotePlugin.cs:157` — `app.Dispatcher.Invoke(action)`
  - `shell-convert/Services/ConvertMenuService.cs:95` — `Dispatcher.Invoke` (密码输入)
  - `shell-settings/SettingsWindow.xaml.cs:74` — `Dispatcher.Invoke(() => OnSectionsChanged(...))`
  - `shell-menu-bar/Services/BluetoothEnumerator.cs:210` — `Dispatcher.Invoke` (设备配对)
- **风险**: 同步 `Dispatcher.Invoke` 会阻塞调用线程直到 UI 线程处理完成；若在 UI 线程调用则直接执行。若后台线程高频调用，可能导致 UI 线程队列堆积
- **状态**: `ASSUMPTION` — 需 profile 确认调用频率与 UI 线程阻塞时间

#### C5: Thread.Sleep 在后台/UI 线程
- **位置**:
  - `shell-desktop/Services/DesktopBrowser.cs:332` — `Thread.Sleep(800)` (文件浏览器排序桥接)
  - `shell-desktop/Services/DesktopBrowser.cs:554` — `Thread.Sleep(SortBridgeIntervalMs)`
  - `shell-context-menu/Sections/MenuManagerSection.cs:135` — `Thread.Sleep(100)`
  - `shell-status/Native/KeyboardLayoutInterop.cs:803-835` — 多处 `Thread.Sleep(50-150)` (输入法切换重试)
- **风险**: Thread.Sleep 阻塞线程池线程，可能导致线程池饥饿；若在 UI 线程则直接卡死 UI
- **状态**: `ASSUMPTION` — 需确认这些 Sleep 所在线程与调用频率

#### C6: 同步等待异步任务 (.Result / GetAwaiter().GetResult())
- **位置**:
  - `kernel-loader/LoaderService.cs:72` — `handle.AwaitAsync().GetAwaiter().GetResult()`
  - `shell-menu-bar/Windows/BluetoothPopupWindow.cs:1143,1242` — `task.Result`
  - `shell-search/Services/FileSearchProvider.cs:134` — `fallbackTask.Result`
  - `shell-dock/Windows/AppGrabberWindow.cs:465` — `startMenuTask.Result.Concat(installedTask.Result)`
  - `shell-context-menu/Services/RegistryVerbs.cs:110` — `hit.Result`
  - `kernel/Core/CordisContext.cs:165` — `plugin.DisposeAsync().GetAwaiter().GetResult()` (Dispose 路径，已登记例外)
- **风险**: 同步等待可能导致死锁 (若 Task 需 UI 线程完成而调用方在 UI 线程)，以及线程池饥饿
- **状态**: `ASSUMPTION` — 需逐个确认调用上下文 (UI 线程 vs 后台线程) 与死锁风险

#### C7: 稳态轮询定时器密度 (空闲 CPU 候选)
- **StatusPoller 独立定时器** (System.Threading.Timer, 线程池线程):
  - CPU: 1000ms, Memory: 1000ms, Network: 1000ms
  - IME: 500ms, Microphone: 500ms, Volume: 500ms
  - Battery: 3000ms, Default: 2000ms
  - 合计: ~7 个定时器，最短间隔 500ms
- **DispatcherTimer** (UI 线程):
  - DockWindow: 至少 6 个 (refresh, sun-sync, auto-hide, recycle-hover 150ms, preview open/close/watchdog)
  - MenuBar 面板: CPU 1s, Memory, Network, Sound, Microphone, Power 5s, Media 2s, Bluetooth 3s
  - 其他: ContextMenu self-heal 800ms, Desktop watchdog, Search debounce 350ms
- **风险**: 大量 DispatcherTimer 在 UI 线程触发，即使单次处理很快，累积也可能导致空闲 CPU 占用和偶发卡顿
- **状态**: `ASSUMPTION` — 需合同 C 测量稳态 CPU 确认

#### C8: 插件加载顺序 — 串行依赖链
- **证据**: Bootstrap.cs 中 20+ 插件硬编码顺序注册，`context.Plugin()` 是 fire-and-forget 但 `PluginHandle.StartAsync()` 内部通过 `SemaphoreSlim(1,1)` 串行化
- **机制**: 虽然 Plugin() 调用立即返回，但每个插件的实际加载 (ReloadAsync) 是串行的 (RestartSerializedAsync)。依赖未满足的插件停在 Pending，等 NotifyDependents 触发重启
- **影响**: 20 插件串行加载，若每个插件 LoadAsync 平均 50ms (含窗口创建)，总加载时间 ~1s。这是启动时间的主要贡献者
- **状态**: `ASSUMPTION` — 需合同 A 测量各插件 LoadAsync 实际耗时，确认串行化是否为瓶颈

#### C9: CompositionTarget.Rendering (DwmThumbnail)
- **位置**: `shell-window-tracker/Thumbnail/DwmThumbnail.cs:102`
- **机制**: 订阅 `CompositionTarget.Rendering` 但仅在 `_dirty` 时执行 Refresh，执行后立即退订 (line 131)。非永久每帧回调
- **评估**: 设计良好，仅在需要时订阅一帧。**低风险**
- **状态**: `ASSUMPTION` (低优先级)

#### C10: CordisContext.Dispose 同步阻塞
- **证据**: `CordisContext.cs:165` — `plugin.DisposeAsync().GetAwaiter().GetResult()`，注释说明"Dispose 路径允许同步等待（非 UI 线程；coding-standards 并发纪律 2 的例外已登记）"
- **测量**: `context-dispose-20-plugins` median 24.6 µs (含构造+加载，纯 Dispose 部分更短)
- **风险**: 若在 UI 线程调用 Dispose 且插件 UnloadAsync 耗时，会阻塞 UI
- **状态**: `ASSUMPTION` — 需确认 Dispose 调用线程
