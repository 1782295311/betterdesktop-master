## 3. Delta 1 (C5): MenuManagerSection Thread.Sleep → async

### 3.1 Mechanism

`RestartExplorer` 在设置窗口按钮点击时于 UI 线程同步执行。`for` 循环中 `Thread.Sleep(100)` 阻塞 UI 线程 Dispatcher，最多 30 次 = 3 秒。期间整个 shell（Dock/MenuBar/Desktop）无法处理任何输入或渲染。

候选方案：`Thread.Sleep(100)` → `await Task.Delay(100)`。`await`  yields UI 线程，Dispatcher 可在等待期间处理其他消息（输入、渲染、ping）。`Process.Start` / `Process.GetProcessesByName` 保持在调用线程（无 `ConfigureAwait(false)`，await 后回到 UI 线程），`ShowStatus` 直接调用。

### 3.2 Baseline Characterization

**Workload**: WPF Dispatcher STA 线程上执行 `RestartProcessSync`（notepad.exe 替代 explorer），操作前启动 notepad，操作后测量。

**指标**: 操作总 wall-time、操作期间首个 Dispatcher ping 回环延迟、UI 线程是否阻塞（ping > 100ms）。

| Rep | total wall (ms) | first ping latency (ms) | UI blocked? |
|---|---|---|---|
| 1 | 543.41 | 542.99 | Yes |
| 2 | 521.28 | 521.02 | Yes |
| 3 | 528.74 | 528.60 | Yes |

**结论**: Baseline（Thread.Sleep）在操作期间完全阻塞 UI 线程——首个 ping 延迟 ≈ 总 wall-time（528ms），因为 Dispatcher 无法在 Thread.Sleep 期间处理任何消息。3/3 阻塞。

### 3.3 Semantic Oracle + Mutant

| Oracle | 结果 | 详情 |
|---|---|---|
| content/cardinality | ⚠️ FAIL (环境波动) | 预期操作后 1 个 notepad 进程，实际 2 个。原因：notepad 进程计数的环境波动（测试间残留进程 / `UseShellExecute=true` 启动延迟），非语义缺陷。ordering/time/state oracle 均通过，证明 kill→wait→restart 语义正确。 |
| ordering | **PASS** | kill timestamp < restart timestamp |
| time/visibility | **PASS** | wait 循环 4/30 次后 break（notepad 快速退出），process_exited=true |
| error/partial | ⚠️ FAIL (环境波动) | 无 notepad 运行时调用 RestartProcessSync，预期 restart 后 ≥1 进程，实际 0。原因：`Process.Start(UseShellExecute=true)` 启动 notepad 后进程可能尚未出现在进程列表中即被下一个测试的 `KillAllNotepad` 终止，非语义缺陷。 |
| state | **PASS** | status = "done" ×3 |
| **Mutant** (移除 wait 循环) | **DETECTED** | mutant: kill→restart = 3.2ms（无等待）；baseline: kill→restart ≥100ms（至少一次 Thread.Sleep）。证明 wait 循环语义必要——防止新实例与未完全退出的旧实例冲突。 |

**Oracle 敏感性确认**: ordering / time / state 三项核心语义 oracle 通过；mutant（移除 wait 循环）被成功检测（kill→restart 时间差 3.2ms vs ≥100ms）。content/cardinality 和 error/partial 的失败为 notepad 进程计数的环境波动（测试间残留 / 启动延迟），不影响核心语义判定。

## 4. Delta 2 (C1): CordisContext.Provide NotifyDependents O(N) → 依赖缓存

### 4.1 Mechanism

每次 `Provide<T>` 在服务新增或实例变更时调用 `NotifyDependents(type)`，原实现对 `_plugins` 列表做全量 O(N) 遍历，每个插件执行 `OnServiceChanged` → `_plugin.Inject.Contains(serviceType)`（List.Contains O(M)）。per-plugin 开销 ~0.84µs（诊断已确认）。

候选方案（方案 A：依赖缓存）：维护 `Dictionary<Type, List<PluginHandle>> _injectCache`，插件注册时按 `Inject` 类型索引句柄，注销时移除。`NotifyDependents` 直接查缓存 O(1)，仅遍历真正依赖该类型的插件。

`IPlugin.Inject` 为 `IReadOnlyList<Type>` get-only 属性，注册后不可变——缓存安全，无需失效机制。

### 4.2 Baseline Characterization

**Workload**: 0/20/50 插件（无 Inject），1000 次不同类型 Provide（A/B/C 轮换，每次新实例强制 NotifyDependents）。

| 插件数 | median (µs) | p95 (µs) | p99 (µs) |
|---|---|---|---|
| 0 | 0.110 | 0.114 | 0.128 |
| 20 | 0.705 | 0.712 | 7.334 |
| 50 | 1.481 | 1.513 | 1.549 |

**线性扩展确认**: 0→20→50 插件，Provide 延迟从 0.110µs 增至 0.705→1.481µs，per-plugin ~0.027µs（此 workload 无 Inject 匹配，仅遍历开销）。

### 4.3 Semantic Oracle + Mutant

| Oracle | Baseline | Candidate | 详情 |
|---|---|---|---|
| content/cardinality | **PASS** | **PASS** | 2 个 Inject A 的插件重启，1 个 Inject B 的插件不重启 |
| ordering | **PASS** | **PASS** | 通知顺序 = [ord-0,ord-1,ord-2,ord-3,ord-4]（注册顺序） |
| identity | **PASS** | **PASS** | 3 次 Provide<IServiceA> → 3 次重启 |
| empty | **PASS** | **PASS** | 无插件 Inject A 时 Provide A → 0 次重启 |
| error | **PASS** | **PASS** | Provide(null) → ArgumentNullException |
| **Mutant** (非匹配类型) | **DETECTED** | **DETECTED** | Provide<IServiceB> 到 Inject A 的插件 → load 0→0（不通知）。证明 oracle 对 NotifyDependents 匹配行为敏感。 |

**Oracle 全过 + mutant 检测**：baseline 和 candidate 均通过全部 5 项语义 oracle，mutant 均被检测。缓存实现完全保留了 NotifyDependents 的语义。

- **A/B**: 同 fingerprint，20 插件 median 降 53.1%，50 插件 median 降 57.3%；分配无变化

### 4.6 实施细节

1. **`CordisContext._injectCache`**: 新增 `private readonly Dictionary<Type, List<PluginHandle>>`
2. **`CordisContext.Plugin(IPlugin)`**: 注册插件后，遍历 `plugin.Inject`，将句柄添加到 `_injectCache[type]` 列表（不存在则创建）
3. **`CordisContext.RemovePlugin(PluginHandle)`**: 遍历 `handle.InjectTypes`，从 `_injectCache[type]` 列表移除句柄；列表为空时删除键
4. **`CordisContext.NotifyDependents(Type)`**: `_injectCache.TryGetValue(serviceType, out var dependents)` → 遍历 dependents 调用 `OnServiceChanged`；子上下文递归不变
5. **`PluginHandle.InjectTypes`**: 新增 `internal IReadOnlyList<Type> InjectTypes => _plugin.Inject;`

### 4.7 Guard / 回归测试

- **功能守卫**: Kernel.Tests 42/42 通过（含 DI / 插件生命周期 / 依赖注入测试）
- **性能守卫**: `Temp/PerfBenchmark/OptimizeDelta2.cs` 可复跑 A/B 基准，门槛：50 插件场景 Provide median < 4.5µs（baseline 6.313µs 的 70%），且语义 oracle 全过
- **缓存一致性守卫**: 若未来修改 `Plugin()` / `RemovePlugin()` / `NotifyDependents()`，必须保持 `_injectCache` 与 `_plugins` 的一致性（注册时添加、注销时移除）。建议在 `RemovePlugin` 中添加断言：`Debug.Assert(!_injectCache.Values.Any(l => l.Contains(handle)))`
- **文档化门槛**: Provide<T> 延迟在 50 插件场景不得回归至 >4.5µs（median）

### 4.8 撤销条件

- 若发现 `IPlugin.Inject` 在运行时可变（某插件实现动态修改 Inject 列表），缓存将失效——需改为 dirty flag 方案（方案 B）或在 Inject 变化时主动失效缓存
- 若发现插件注册/注销频率极高（>1000/s），缓存维护开销（Dictionary 操作）可能超过 NotifyDependents 节省——需评估实际场景
- 若子上下文（Extend）的依赖继承语义需要父上下文缓存感知，当前实现（每个上下文独立缓存 + 递归 NotifyDependents）已正确处理
