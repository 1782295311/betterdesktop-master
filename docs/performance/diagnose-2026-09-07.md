## 3. Delta Dossier (逐候选)

### 3.1 C1: NotifyDependents O(N) 遍历

#### mechanism

每次 `Provide<T>` 在服务新增或实例变更时, 调用 `NotifyDependents(type)`, 对 `_plugins` 列表做全量 O(N) 遍历. 每个插件执行 `OnServiceChanged` → `_plugin.Inject.Contains(serviceType)` (List.Contains, O(M) where M=该插件 Inject 类型数). 若 Inject 匹配则触发 `RestartSerializedAsync` (fire-and-forget).

#### delta fingerprint

| 插件数 N | Provide 延迟 (µs) | 增量 (µs) | per-plugin (µs) |
|---|---|---|---|
| 0 | 0.311 | — | — |
| 5 | 5.569 | 5.258 | 1.052 |
| 10 | 8.807 | 3.238 | 0.648 |
| 20 | 17.067 | 8.260 | 0.826 |
| 50 | 49.372 | 32.305 | 0.646 |

**线性拟合**: 延迟 ≈ 0.31 + 0.84×N µs (R² > 0.99). per-plugin 开销稳定在 0.65-1.05µs, 包含 foreach 迭代 + 虚方法调用 OnServiceChanged + List.Contains on Inject.

#### touched boundaries

- `_services` Dictionary (写入)
- `_plugins` List (只读遍历)
- 每个 PluginHandle 的 `_restartGate` (若 Inject 匹配)
- 子上下文递归 (若存在 Extend)

#### protected semantics

- 服务实例替换: 必须通知所有依赖方重启 (epoch 语义 v1 = 实例粒度)
- 依赖检查: `AllDependenciesAvailable()` 必须在重启时重新评估
- 线程安全: `NotifyDependents` 无锁, 依赖 PluginHandle 内部锁保护状态
- 顺序: 遍历顺序 = 注册顺序 (Bootstrap 硬编码顺序)

#### baseline characterization

- `provide-get-no-plugins`: 0.513µs (2 Provide + 2 Get, 无 NotifyDependents)
- `provide-get-with-20-plugins`: 17.656µs (2 Provide + 2 Get, 含 2 次 NotifyDependents × 20 插件)
- 单次 NotifyDependents (20 插件, 无 Inject 匹配): ~8.5µs
- 比率: 34.4x (20 插件 / 无插件)

#### minimum counterexample

**替代解释 1: 首次 Provide 冷启动开销, 后续有缓存**
- 反证: 基准包含 50 次 JIT warmup + 每次 rep 前 GC.Collect. 2000 次迭代中位数稳定 (stddev 4%), 无冷启动效应. 且代码中无缓存机制 — `NotifyDependents` 每次都全量遍历.
- **裁决: REJECTED**

**替代解释 2: Dictionary 查找本身的开销**
- 反证: 0 插件时 Provide 仅 0.311µs (含 Dictionary 写入 + ContainsKey + 索引). 20 插件时 17.067µs. Dictionary 操作在两种情况下相同, delta 16.756µs 完全来自 NotifyDependents 遍历.
- **裁决: REJECTED**

#### mutant sensitivity

- **Inject 不匹配 (20 插件 Inject IServiceB, Provide IServiceA)**: 17.673µs — 与无特定 Inject 的 17.067µs 一致 (差异 <4%), 确认 List.Contains on empty/wrong Inject 是主要开销, 不触发 RestartSerializedAsync.
- **Inject 全匹配 (20 插件 Inject IServiceA, Provide IServiceA)**: 29.936µs — 比不匹配高 69%, 确认 RestartSerializedAsync (SemaphoreSlim.WaitAsync + ReloadAsync 状态切换) 增加额外开销. 注意: 此测量包含等待所有插件重启完成的时间.
- **同实例重复 Provide**: 第一次 Provide 触发 NotifyDependents (~17µs), 第二次 Provide 同一实例因 `ReferenceEquals(previous, service)` 跳过 NotifyDependents (~2.6µs). 两次平均 9.8µs, 确认跳过机制有效.

#### state

**CONFIRMED** — 机制命中: NotifyDependents 每次 Provide 全量 O(N) 遍历, 无缓存/增量更新. per-plugin 开销 ~0.84µs. 20 插件时单次 Provide 含 NotifyDependents = ~17µs.

**累积影响估算 (内核层)**: Bootstrap 启动序列 (4 Provide + 20 插件 + 5 次插件内 Provide) 总内核耗时 = 53.7µs (median). 即使 Provide 调用翻倍, 内核层累积 < 200µs. **对启动时间影响有限** (真实启动耗时在插件 LoadAsync 内部, 见 C8).

### 3.2 C2: EventBus.Snapshot 每次 emit 分配 List

#### mechanism

每次事件分发 (Emit/Parallel/Serial/Bail/Waterfall) 调用 `Snapshot(name)`, 在 `lock(_gate)` 中执行 `list.ToList()`, 分配新的 `List<HandlerEntry>` 对象 + 数组. 该列表在分发完成后成为垃圾, 由 GC 回收.

#### delta fingerprint

| handler 数 | 每次 Emit 分配 (bytes) | 增量 (bytes) | per-handler (bytes) |
|---|---|---|---|
| 0 | 240 | — | — |
| 1 | 432 | 192 | 192 |
| 10 | 960 | 720 | 72 |
| 50 | 3056 | 2816 | 56 |

- 0 handler 基准 240B: async/Task 状态机分配 (EmitAsync 是 async 方法, 即使无 handler 也分配 Task/状态机)
- per-handler 56-72B: 符合 `List<HandlerEntry>` 分配 = List 对象头 (~32B) + T[] 数组 (~24B + 8×count) + 对齐填充
- **GC 压力**: 10,000 次 Emit (10 handlers) = 9.6MB 分配, **触发 0 次 Gen0 GC** (Gen0 预算 ~16MB, 分配量未超阈值)

#### touched boundaries

- `_handlers` Dictionary (lock 内只读)
- `_gate` lock (每次 Snapshot 获取/释放)
- GC 堆 (分配 List<HandlerEntry> + 数组)

#### protected semantics

- 线程安全: Snapshot 在 lock 内创建副本, 使分发期间 handler 列表不受并发注册/注销影响
- 枚举安全: 遍历副本而非原始列表, 避免 handler 在遍历中被修改
- 异常隔离: 单个 handler 异常不影响其他 handler (RunQuiet try-catch)

#### baseline characterization

- `eventbus-emit-1-handler`: 12.3µs (含 100 次 emit/iter, 即 ~0.12µs/emit — 等等, 不对)
- 实际: benchmark 中每次 iter 执行 100 次 emit, 总耗时 / iter = 12.3µs, 即单次 emit = 0.123µs? 不对, 让我重新算...
- 基准 `eventbus-emit-1-handler`: iterations=10000, 每次 iter 创建新 context + 订阅 + 100 次 emit. median=0.012267 ms/op = 12.267µs per iter. 100 次 emit + context 创建 + 订阅, 所以单次 emit < 12.267µs.
- 诊断基准 `c2-emit-allocation-1-handlers`: 1000 iter × 3 reps, 每次 iter 创建 context + 订阅 + 预热 1 次 + 100 次 emit 测量分配. median=432 bytes/op.

#### minimum counterexample

**替代解释 1: 事件频率低, 分配可忽略**
- 部分确认: 10k 次 emit (10 handlers) = 0 Gen0 GC. 在低频场景 (<100 emit/sec), 日分配量 < 10MB, GC 压力可忽略.
- 但: 若存在高频事件 (如鼠标移动 ~60-120Hz, 窗口位置变化, 状态轮询变更广播), 1000 emit/sec × 960B = 57.6MB/min, 可能触发频繁 Gen0 GC.
- **裁决: EVIDENCE_REQUIRED** — 需确认生产环境中各事件的实际发射频率. 静态分析显示 StatusPoller 每次状态变化都 EmitAsync("status.changed"), 7 个监控项 × 变化频率可能较高.

**替代解释 2: ToList 是线程安全的必要设计**
- 确认: Snapshot 的 ToList 是为了在 lock 外遍历 handler 列表, 避免长时间持有锁. 这是合理的线程安全设计.
- 但: 替代方案 (如 ImmutableList + 引用交换, 或读写时直接 lock 遍历) 可减少分配, 但可能改变锁粒度/语义.
- **裁决: CONFIRMED 设计必要性, 但分配量可测量**

#### mutant sensitivity

- 0 handler: 240B (纯 async 状态机分配, 无 List 分配 — Snapshot 返回 `new List<HandlerEntry>()` 空列表, 但 240B 主要是 Task 分配)
- 实际上 0 handler 时 Snapshot 仍分配空 List (~56B), 加上 async 状态机 ~184B = 240B
- 50 handler: 3056B, per-handler 递减 (56B) 因为 List 容量对齐 (ToList 分配精确容量, 无额外容量)

#### state

**CONFIRMED (机制) / LOW_IMPACT (当前测量条件下)**

机制命中: 每次事件分发分配 List<HandlerEntry>, per-handler 56-72B. 10k 次 emit (10 handlers) 未触发 Gen0 GC.

**未验证**: 生产环境事件频率. 若高频事件 (>500/sec) 存在, GC 压力可能显著. 需完整 shell 运行时用 dotnet-counters 监控 Gen0 GC 速率 + 事件计数.

### 3.3 C3: ParallelAsync 高方差

#### mechanism

`ParallelAsync` 使用 `Task.WhenAll` 等待 N 个 handler 任务. 即使所有 handler 同步完成 (`Task.FromResult`), `Task.WhenAll` 仍需创建延续任务并由线程池调度, 引入高尾延迟.

#### delta fingerprint

| 指标 | Median (µs) | StdDev (µs) | CV (%) |
|---|---|---|---|
| ParallelAsync (10 sync handlers, 50 call/iter) | 41.5 | 35.8 | **86%** |
| SerialAsync (10 handlers, 50 call/iter) | 38.5 | 0.8 | **2%** |
| ParallelAsync (单次调用分布, 1000 iter) | 6.5 | — | — |

- ParallelAsync 中位数仅比 SerialAsync 高 8% (41.5 vs 38.5µs), 但方差高 43 倍
- 单次 ParallelAsync 调用 (非批量): 6.5µs — 批量 50 次的均值 41.5µs 包含了 context 创建/订阅开销
- 高方差样本: max=103.3µs (2.5× median), 典型线程池调度尾延迟

#### touched boundaries

- 线程池 (Task.WhenAll 延续调度)
- GC 堆 (Task 对象 + 延续委托分配)
- `Snapshot` (同 C2)

#### protected semantics

- 并发执行: 所有 handler 并发执行 (Task.WhenAll)
- 结果过滤: null 结果被过滤 (`Where(r => r is not null)`)
- 异常隔离: 单个 handler 异常被 RunTypedQuiet 捕获, 返回 default
- 顺序: 结果顺序 = handler 注册顺序 (Task.WhenAll 保持顺序)

#### baseline characterization

- `eventbus-parallel-10-handlers`: median 48.1µs, stddev 71% (基线)
- 诊断复现: median 41.5µs, stddev 86% — 高方差可复现
- `eventbus-serial-10-handlers`: median 36.0µs, stddev 3.4% (基线)
- 诊断复现: median 38.5µs, stddev 2% — 低方差可复现

#### minimum counterexample

**替代解释 1: handler 执行时间本身方差大**
- 反证: 诊断使用 `Task.FromResult(v * 2)` — 纯同步, 零 IO, 执行时间恒定. 方差不可能来自 handler 执行.
- **裁决: REJECTED**

**替代解释 2: 在 UI 线程调用 ParallelAsync 导致 Dispatcher 调度方差**
- 未验证: 诊断基准在控制台线程池线程运行, 无 UI 线程/Dispatcher. 高方差在无 UI 环境下仍存在, 说明来自 Task.WhenAll/线程池本身, 而非 Dispatcher.
- 但: 生产环境中若 ParallelAsync 在 UI 线程调用, 方差可能更高 (Dispatcher 调度叠加).
- **裁决: 基础机制 CONFIRMED (线程池调度), UI 线程叠加效应 EVIDENCE_REQUIRED**

#### mutant sensitivity

- 同步 handler (Task.FromResult): 方差 86% — 确认方差来自 Task.WhenAll 调度, 非 handler 执行
- SerialAsync 对照: 方差 2% — 确认顺序 await 无并发调度方差
- 单次调用: 6.5µs — 远低于批量均值, 说明批量测量中 context 创建/订阅占主导

#### state

**CONFIRMED** — 机制命中: ParallelAsync 的高方差来自 `Task.WhenAll` 线程池调度尾延迟, 与 handler 执行时间无关 (同步 handler 仍 86% CV). SerialAsync 对照方差仅 2%.

**用户感知影响**: 未验证. 若 ParallelAsync 在 UI 线程热路径 (如窗口打开、菜单弹出) 调用, 尾延迟 100µs 级可能叠加导致帧时间超标. 需确认生产代码中 ParallelAsync 的调用线程与频率.

### 3.4 C8: 20 插件串行加载 (原假设 REJECTED)

#### mechanism (原假设)

`PluginHandle.RestartSerializedAsync` 使用 `SemaphoreSlim(1,1)` 串行化所有插件加载, 20 个插件的 LoadAsync 总耗时 = 各插件耗时之和.

#### 反证 (运行证据)

| 实验 | 结果 | 预期 (串行) | 预期 (并发) |
|---|---|---|---|
| 20 插件 × 50ms delay, 全部注册后统一 await | **61.3ms** | ~1000ms | ~50ms |
| 20 插件 × 50ms delay, 逐个注册+立即 await | **1246.4ms** | ~1000ms | ~1000ms (逐个 await 强制串行) |
| 20 插件同步 LoadAsync (无 delay) | **8.5µs** | ~20×单插件 | ~单插件 |

- **并发加载确认**: 20 插件各延迟 50ms, 总耗时 61.3ms ≈ 50ms + 调度开销. 若串行应为 ~1000ms.
- **逐个 await 是测量伪影**: Bootstrap 不逐个 await — 它注册所有插件 fire-and-forget, 不等待. 逐个 await 1246ms 是因为每次 AwaitAsync 阻塞到该插件完成才注册下一个, 人为制造了串行.
- **SemaphoreSlim 是 per-instance**: `_restartGate` 声明为 `private readonly` (非 static), 每个 PluginHandle 有自己的信号量. 插件之间不共享锁, 互不阻塞.

#### 修正后的机制理解

插件加载实际是**并发启动 + 依赖驱动级联**:

1. `CordisContext.Plugin()` → `_ = handle.StartAsync()` (fire-and-forget, 立即返回)
2. 所有无依赖插件的 `LoadAsync` 并发执行 (线程池)
3. 有依赖但依赖未满足的插件停在 Pending
4. 当某个插件 Provide 了依赖服务 → `NotifyDependents` → 依赖方插件 `OnServiceChanged` → `RestartSerializedAsync` (fire-and-forget) → 开始加载
5. 依赖链可以级联: A Provide → B 加载 → B Provide → C 加载...

**依赖链行为关键发现**: 服务 Provide 发生在 LoadAsync 的哪个位置决定了级联是串行还是并行:
- 若 Provide 在 LoadAsync **早期** (如构造函数/同步部分), 依赖方立即被触发, 后续 delay/IO 可重叠 → 近似并发
- 若 Provide 在 LoadAsync **晚期** (如窗口创建后/IO 完成后), 依赖方必须等前置插件完全完成 → 严格串行
- 诊断基准中 onLoad (Provide) 在 Task.Delay 之前执行, 所以 5 级依赖链总耗时 15.5ms (所有 delay 重叠), 而非预期的 50ms 串行

#### touched boundaries

- 线程池 (并发 LoadAsync 调度)
- `_plugins` List (注册)
- 每个 PluginHandle 的 `_restartGate` (per-instance, 仅序列化同一插件的多次重启)
- `NotifyDependents` (依赖级联触发)

#### protected semantics

- 依赖顺序: 插件必须在依赖服务可用后才能加载 (`AllDependenciesAvailable` 检查)
- 错误隔离: 单个插件 LoadAsync 异常 → Failed, 不影响其他插件
- 重启幂等: 同一插件多次服务变更通过 SemaphoreSlim 串行化, 避免并发重启覆盖 `_current`
- 注册顺序: Bootstrap 硬编码顺序确保依赖方在被依赖方之后注册 (但实际加载由依赖检查驱动, 非注册顺序)

#### minimum counterexample

**替代解释 1: 启动时间主要由 WPF 窗口创建/渲染主导**
- PLAUSIBLE — 内核调度 (注册 + 依赖检查) 仅 8.5µs (20 同步插件). 真实插件 LoadAsync 包含 WPF 窗口创建 (DockWindow, MenuBarWindow, DesktopWindow, StartMenuWindow 等), 每个窗口创建可能 10-100ms. 这些窗口创建虽然并发启动, 但 WPF UI 线程是单线程的 — 所有窗口的构造/布局/渲染必须在 UI 线程串行执行.
- **裁决: EVIDENCE_REQUIRED** — 需完整 shell 启动分段测量 (合同 A) 确认 WPF 窗口创建占总启动时间比例. 静态分析显示 10+ 个 WPF Window 在插件 LoadAsync 中创建, UI 线程串行化可能是真实瓶颈.

**替代解释 2: 线程池饥饿导致并发受限**
- 部分相关: 20 插件并发加载, 若每个 LoadAsync 都阻塞线程池线程 (如 Thread.Sleep, 同步 IO), 线程池可能需要增长. .NET 线程池默认每秒增长 1 个线程 (Hill Climbing), 20 个阻塞任务可能需要数秒才能全部调度.
- 但: 诊断基准中 20 × 50ms Task.Delay 仅 61ms, 说明 Task.Delay (非阻塞) 不导致线程池饥饿. 真实插件中若有 Thread.Sleep/同步 IO, 可能不同.
- **裁决: EVIDENCE_REQUIRED** — 需确认各插件 LoadAsync 中是否有阻塞调用 (C5/C6 已发现部分).

#### mutant sensitivity

- 无 delay 同步加载: 8.5µs (20 插件) — 内核调度极快
- 50ms delay 并发: 61ms — 确认并发
- 50ms delay 逐个 await: 1246ms — 确认逐个 await 是人为串行
- 5 级依赖链 (Provide 在 delay 前): 15.5ms — 确认早期 Provide 使级联并发
- 5 级依赖链 (若 Provide 在 delay 后): 预期 ~50ms 串行 — 未测量, 但逻辑可推

#### state

**REJECTED (原机制: 全局串行加载) / CONFIRMED (修正机制: 并发启动 + 依赖级联 + UI 线程串行化)**

原假设 "SemaphoreSlim 全局串行化插件加载" 被运行证据反证: SemaphoreSlim 是 per-plugin 实例, 插件实际并发加载 (20×50ms = 61ms).

**真实启动瓶颈候选**: WPF UI 线程串行化 (10+ 窗口创建) + 插件 LoadAsync 内的阻塞调用 (Thread.Sleep/同步 IO) + 依赖链晚期 Provide 导致的级联串行. 这些需完整 shell 测量确认.

### 3.5 C4: Dispatcher.Invoke 同步阻塞

#### mechanism (假设)

后台线程调用 `Dispatcher.Invoke` 同步阻塞, 等待 UI 线程处理完成. 若高频调用或 UI 线程繁忙, 可能导致线程池阻塞和 UI 响应延迟.

#### 静态分析证据

| 位置 | 调用模式 | 线程上下文 | 守卫 | 频率 |
|---|---|---|---|---|
| `DesktopWindow.cs:227` | `Dispatcher.Invoke(() => ...)` | STA worker 线程 (跨进程委托) | 无 CheckAccess | 桌面菜单交互时 |
| `QuickNotePlugin.cs:156` | `app.Dispatcher.Invoke(action)` | 可能后台 (LoadAsync ConfigureAwait(false)) | CheckAccess 守卫 | 快速笔记窗口创建/销毁 |
| `ConvertMenuService.cs:95` | `Dispatcher.Invoke` (密码输入) | 转换服务后台线程 | 无 | 文件转换时 (用户触发) |
| `SettingsWindow.xaml.cs:77` | `Dispatcher.Invoke(() => OnSectionsChanged(...))` | 插件 LoadAsync 线程池 | CheckAccess 守卫 | 插件注册设置分区时 (启动期) |
| `BluetoothEnumerator.cs:210` | `app.Dispatcher.Invoke(() => PairDeviceCore(...))` | 蓝牙枚举后台线程 | 无 | 设备配对时 (用户触发) |

#### 关键发现

- **CheckAccess 守卫模式**: QuickNotePlugin 和 SettingsWindow 先检查 `Dispatcher.CheckAccess()`, 若已在 UI 线程则直接执行, 否则才 Invoke. 这是标准 marshalling 模式, 仅在跨线程时阻塞.
- **无守卫的 Invoke**: DesktopWindow (STA worker), ConvertMenuService (密码对话框), BluetoothEnumerator (配对) — 这些总是同步阻塞调用线程.
- **频率**: 所有 Dispatcher.Invoke 都是事件驱动 (用户交互/插件加载), 非稳态轮询. 启动期 SettingsWindow 的 Invoke 可能发生多次 (每个插件注册分区), 但启动期一次性.

#### minimum counterexample

**替代解释: 某些 Invoke 实际在 UI 线程调用, 不阻塞**
- 部分确认: CheckAccess 守卫的两处 (QuickNote, SettingsWindow) 若在 UI 线程调用则直接执行, 不阻塞. 但 SettingsWindow.OnSectionsChanged 注释明确说 "注册可能发生在非 UI 线程 (插件 LoadAsync 线程池)", 所以确实会跨线程 Invoke.
- **裁决: 部分 REJECTED (有守卫的), 其余 EVIDENCE_REQUIRED**

#### state

**EVIDENCE_REQUIRED** — 静态分析确认 5 处 Dispatcher.Invoke, 其中 2 处有 CheckAccess 守卫. 所有调用均为事件驱动, 非稳态高频. 实际 UI 线程阻塞时长需 profile 确认 (需完整 shell 运行 + 线程时间线).

### 3.6 C5: Thread.Sleep 阻塞

#### 静态分析证据

- **KeyboardLayoutInterop.cs**: 6 处 Sleep 在 IME 切换重试循环中,  likely 后台线程.

#### minimum counterexample

**替代解释: 某些 Sleep 在非 UI 线程, 不影响流畅度**
- 确认: DesktopBrowser 和 KeyboardLayoutInterop 的 Sleep 在后台线程, 不直接阻塞 UI. 但可能导致线程池饥饿 (若多个后台任务同时 Sleep).
- **裁决: 部分 CONFIRMED (MenuManagerSection UI 线程), 其余 LOW_IMPACT**

#### state

**EVIDENCE_REQUIRED** (1 项确认 UI 线程阻塞, 其余后台线程)

- MenuManagerSection: CONFIRMED UI 线程阻塞最多 3s (用户主动操作, 一次性)
- DesktopBrowser/KeyboardLayout: 后台线程 Sleep, 不直接阻塞 UI, 但可能贡献线程池压力
- 实际流畅度影响需完整 shell 运行时 UI 线程响应性测量确认

### 3.8 C7: 定时器轮询密度 (空闲 CPU 候选)

#### 定时器清单 (静态分析)

**System.Threading.Timer (线程池线程, 始终运行)**:

| 所属 | 数量 | 间隔 | 回调工作 |
|---|---|---|---|
| StatusPoller | 7 | 500ms (IME/Mic/Volume), 1000ms (CPU/Mem/Net), 2000ms (default), 3000ms (Battery) | 采集系统状态, 变化时 EmitAsync |
| ResourceGovernor | 1 | 5000ms | 采样内存/CPU, 超阈值告警 |
| SettingsService | 1 | debounce (Timeout.Infinite 默认) | 仅设置变更后启动, flush 到磁盘 |
| StartMenuWatcher | 1 | debounce | 仅开始菜单变更后启动 |
| WindowTrackerService | 1 | debounce | 仅窗口变化后启动 |
| DesktopBrowser | 1 | debounce | 仅文件系统变化后启动 |

**DispatcherTimer (UI 线程, 始终运行的)**:

| 所属 | 数量 | 间隔 | 回调工作 |
|---|---|---|---|
| DockWindow | 3+ | refresh (未知), sun-sync (未知), auto-hide (未知) | 刷新 Dock 图标/位置, 日出日落同步, 自动隐藏检查 |
| DockWindow | 1 | 150ms (recycle-hover) | 回收站悬停检测 |
| MenuBarStatusStrip | 4 | status (未知), clock (1s?), network speed (未知), signal (5s) | 更新状态栏图标/文本 |
| MenuBarWindow | 1 | idle (未知) | 空闲检测 |

**条件性 DispatcherTimer (仅弹窗/悬停时激活)**:
- 各 PopupWindow (Wifi/Bluetooth/Sound/Power/Network/Memory/Microphone): 每个 1 个 refresh timer (1-5s), 仅弹窗打开时
- Dock preview timers (open/close/watchdog): 仅悬停预览时
- StartMenu search debounce (250ms): 仅搜索时
- ContextMenu self-heal (800ms): 仅菜单显示时

#### 关键发现

- **始终运行的线程池定时器**: ~9 个 (7 StatusPoller + 1 Governor + 若干 debounce, 但 debounce 默认不启动). 最短间隔 500ms (3 个), 即每秒至少 6 次线程池唤醒.
- **始终运行的 DispatcherTimer**: ~8+ 个 (Dock 4 + MenuBar 4), 最短 150ms (Dock recycle-hover).
- **回调工作量**: StatusPoller 回调执行实际系统状态采集 (CPU/内存/网络 P/Invoke, 可能 0.1-1ms), 变化时 EmitAsync. Dock/MenuBar 的 DispatcherTimer 多为检查标志 + 条件更新 UI.
- **事件驱动补充**: StatusPoller 还启动了 WinEvent 前台泵和电源广播钩子, 部分状态变化由事件驱动而非轮询 (减少轮询频率需求).

#### minimum counterexample

**替代解释: 定时器回调非常轻量 (仅检查标志), 实际 CPU 影响可忽略**
- PLAUSIBLE — 许多 DispatcherTimer 回调仅检查 dirty 标志, 无变化时直接返回 (亚微秒级). StatusPoller 的 500ms 定时器执行实际 P/Invoke 采集, 但 3 个 500ms 定时器 = 每秒 6 次采集, 每次假设 0.5ms = 0.3% CPU 占用.
- 但: 若回调中存在意外的重计算 (如全量 UI 刷新、字符串分配), 累积可能显著.
- **裁决: EVIDENCE_REQUIRED** — 需稳态 CPU 测量 (合同 C) 确认实际空闲 CPU 占用. 静态分析无法量化回调实际工作量.

#### state

**EVIDENCE_REQUIRED** — 静态分析确认 ~9 个始终运行的线程池定时器 + ~8 个始终运行的 DispatcherTimer, 最短间隔 150ms. 但回调实际工作量和 CPU 占用需完整 shell 稳态测量确认. 替代解释 (轻量回调) 合理但未验证.
