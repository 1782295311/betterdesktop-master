# defensive-patterns.md — 防御性模式

> 地位：来之不易的缺陷类别规则。每条都是「实际发布或差点发布」的一类缺陷，以「防止复发」的规则形式陈述。
> 来源：`参考/deepseek-harness-master/docs/defensive-patterns.md`，已从 TS/Node 适配到 C#/.NET 桌面外壳。
> 写生命周期、并发、子进程、清理（dispose）代码之前必读。测试层的对应规则见 [`docs/testing.md`](testing.md)。

## 一、正交结果独立上报

一个操作可以同时具有多种独立性质：进程可能已经超时，却仍以退出码 0 结束（因为它捕获了终止信号）；一次取消可能既触发「已停止」又触发「已释放」。每个独立事实（超时、信号、退出码、是否已处置）都要**单独上报**，不要把其中一个标志的上报嵌套在另一个标志的分支里——否则调用方会把提前终止的运行误判为正常成功。

## 二、公共约定两侧都要遵守

当实现收到同一结果的多种表示时，应在通过公共 API 返回前**规范化**。例如某能力接口既可能抛异常、也可能通过事件/结果对象上报失败，中间层必须收敛成唯一形态对外暴露，使消费方不必猜测捕获到的异常究竟来自提供方、包装层还是自身装配逻辑。在类型定义处记录规范化后的约定，并用真实消费方覆盖每种来源形态。

## 三、异步状态不是同步状态

异步操作没有逐消息的完成状态；后台任务的完成与轮次边界存在竞争；取消或释放可能丢弃尚未启动的项。不要把某个聚合状态（如 `Idle`、`Running`）当作某一次调用的结果——多条已排队的工作可能共享同一个运行区间。真正拥有一次运行的调用方必须**显式定义其区间**，并把选取的任何输出描述为整个区间的输出，而不是把因果归于某一条消息。这条守则是双向的：如果等待的转换永远不会发生，等待就会挂起，因此必须显式处理「无需等待」的分支。

## 四、dispose 必须完全停稳，而不仅仅是请求停止

如果清理流程只发出终止/取消信号便返回，而不等待工作真正停止，就会留下孤儿进程或泄漏句柄。清理逻辑必须采用异步流程并**等待**子进程退出（发信号后等待完成）；同时在终止前关闭监听器注册表与通知注册表，使迟到的完成事件保持静默。禁用终结器兜底（对应 [`docs/coding-standards.md`](coding-standards.md)「并发与线程模型」第 6 条）。

## 五、在分发器中隔离回调异常

用户/插件提供的监听器如果抛异常，不得导致它所在的调用被中断，也不得饿死排在它后面的监听器。事件分发循环必须用 `try/catch` 包裹并记录日志——一个行为不当的订阅者绝不能破坏核心生命周期。（内核事件总线的「五种分发」必须满足此条。）

## 六、绝不把环境变量或可预测路径暴露给不可信输出

启动的子进程应使用**已清理的环境变量**，移除名称匹配 `*KEY*`、`*SECRET*`、`*TOKEN*`、`*PASSWORD*` 的项，防止凭证通过命令输出、`env` 或转储文件泄漏。临时文件与转储文件放权限受限的私有目录，用随机文件名，并以独占、仅所有者可访问的方式打开；可预测且全局可读的路径会引发符号链接竞态与信息泄露。

## 七、删除「链接形态」路径用删除链接本身的方式

可能是符号链接或 Windows junction 的路径，必须先判断其重解析点属性，再按「删除链接本身」处理——这样做只会删掉链接而拒绝真实目录，绝不会跟随链接进入其目标。对 junction 直接递归删除可能穿过 junction 进入目标目录；真实目录才使用递归删除。

## 机检现状（诚实标注）

以上七条均为「运行时行为/生命周期」类缺陷，当前**无专门机检**；由 `docs/code-review.md` 评审与「插件卸载必须可完成」架构测试共同把关，后续按需补充针对性的崩溃注入/泄漏演练物证。
