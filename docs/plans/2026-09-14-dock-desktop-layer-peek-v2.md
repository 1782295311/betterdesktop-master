# Dock 缩略图预览回归 v2（原生 peek）+ 桌面层「正本/副本」双实例

> 状态：**方案已定，待实施**；日期 2026-09-14；触发：用户真机复盘
> 相关：`packages/shell/shell-window-tracker/Thumbnail/{WindowPeek,ThumbnailWindow,PreviewWindow}.cs`、`packages/shell/shell-dock/DockWindow*.cs`、`packages/shell/shell-desktop/Windows/DesktopWindow.cs`（桌面嵌入先例）

## 1. 决策链（三次转向，必须记住为什么）

| 阶段 | 方案 | 结论 |
|---|---|---|
| v1 | `SetWindowPos` 抬窗（改 Z 序） | ❌ 对**管理员窗口**被 UIPI 拒绝（err=5），peek 失效 |
| **v2** | `DwmActivateLivePreview(1, target, calling, AeroPeekType.Window)`（cairoshell 标准做法，DWM 合成器层，**免疫 UIPI**） | ⚠️ 被否决，**唯一原因是副作用**：把**除目标外所有顶层窗口**透明化 → dock 与缩略图浮层一起消失 → 「只能看、点不进去」 |
| v3 | 悬停浮层 → 屏幕中央**自绘大图预览层**（`DwmRegisterThumbnail` 放大到工作区 65–75%） | ✅ 落地过；**2026-09-14 用户复盘判其不是真货**：画面虽为原生实时内容，但**宿主是我们的窗口**，观感是"自绘"而非真窗口 |
| **回归 v2** | 前提是让 dock 在 peek 期间存活 | ✅ **本次决定** |

## 2. 关键真相（决定了方案形态，别再猜）

1. **peek 的透明化按「是不是顶层窗口」判定，与 Z 序无关。**
   → 「dock 沉底 / 不置顶 / `EXCLUDED_FROM_PEEK`」**都挡不住**它（后者真机实测无效）。
   → 桌面图标能存活，是因为它是 `SHELLDLL_DefView` 下的 `SysListView32` **子窗口**，不是顶层窗口。
2. **成为桌面子窗口 = 免疫透明化，但同时也盖不住任何普通窗口。**
   → 与现行交互「平时沉底、靠近/贴底热区/悬停时**临时置顶**唤出」**结构性冲突**。
3. 因此：**同一个实例不可能既免疫 peek 又随时可召唤。**
4. ✅ **peek 期间被变暗（视觉上近乎消失）的窗口，仍然收得到鼠标**（2026-09-14 真机实证：浮层已看不见，但鼠标移到对应位置，**点击激活与悬停切换窗口都照常工作**）。
   ⇒ **交互不依赖可见性。** 于是 §3「正本（桌面层实例）」的前提（"让 peek 期间还能操作"）**不成立**——操作本来就不缺，缺的只是"看得见"；而"看得见"在 peek 机制下给不了我们的窗口（除桌面层，而桌面层 2026-09-14 实测不可操控）。
   ⇒ **结论：不做正本/副本**（§3 / §4 / §6 一并作废，留档说明理由）。v2 单独成立：悬停格 → 原生 peek → 移开/点击退出。
5. 唯一遗留的体验缺口：**peek 期间浮层看不见**（"盲点"）——用户判为可接受（"也还好"）。若将来要补，方向不是副本，而是"让浮层在 dimming 下仍可辨识"或"peek 期间给出屏幕位置提示"。

## 3. 方案：正本 / 副本双实例（用户 2026-09-14 提出）

| | **正本**（桌面层实例） | **副本**（顶层实例，= 现行 `DockWindow`） |
|---|---|---|
| 层级 | `SetParent` 到 `SHELLDLL_DefView` 子窗口 | 顶层（现行） |
| 职责 | **peek / 缩略图交互期间**的那一个（免疫透明化） | **平时**的召唤交互（沉底 + 靠近/贴底热区临时置顶） |
| 可见时机 | **仅 peek 期间** | **除 peek 期间外** |

**几何与内容完全一致**（"副本与正本重叠"）：

- 同步**不手工镜像**，两者订阅**同一组单源服务**：`IDockAppsService`（固定项）、`IDockLayoutService`（位置/可见性）、`IWindowTrackerService`（运行项）、`IAppearanceService`（外观）。服务已 Provide → 天然共享。
- **互斥可见性**（关键，否则重影 + 双份热区）：任一时刻**只有一个实例可见且 `IsHitTestVisible=true`**；切换看门狗保证不出现"两个都在"或"两个都无"。

## 4. 分步实施（每步独立可验收，失败即回退）

1. **正本落地**：新增 `DockWindow` 的桌面层版（或同类的第二个实例），挂 `SHELLDLL_DefView` + 提 `HWND_TOP` + `ShowWindow(SW_SHOW)`。
   先例：`DesktopWindow.TryEmbedDesktop()`（**必须走"挂 DefView + 提 HWND_TOP"**；历史红线：沉 `WorkerW` 层会**收不到鼠标输入**，真机已否决）。
   **验收结果（2026-09-14 真机）**：❌ **未通过** —— 挂载本身成功（日志实证 `embedded host=0x540D82(SHELLDLL_DefView) rect=762,1306 1037x122`，可复现两次），**但 dock 不可操控**。与自绘桌面当年「沉 WorkerW 层 → 收不到任何鼠标输入」是**同一种死法**（本次挂的是 DefView，结论相同）。
   **待试一轮补救（合并一次做完）**：① 去掉窗口的 `WS_EX_LAYERED` / 确认基类没设 `WS_EX_TRANSPARENT`——分层与点击穿透都会让子窗口收不到输入，**最可疑**；② 顺序改为 `SetParent` → `ShowWindow` → `SetWindowPos(HWND_TOP)`；③ 挂载后提到宿主子窗口栈顶再 SHOW 并 `SetFocus`。
   **若这一轮仍不可操控 → 正式否决"桌面层可交互"**，则 §3（正本/副本）与 §6（交接协议）**一并作废**；此时「peek 亮出真窗」与「peek 期间我们的 UI 仍可交互」被证实**互斥** ⇒ **多窗口场景下 peek 不可行**（与用户最初判断一致）→ 回到 v3，并把 v3 做扎实（无边框 / 无装饰 / 按真实窗口比例 / 无阴影），而不是继续在 peek 上找出路。
   必须带**失联看门狗**（壁纸引擎会重建桌面层把外来子窗口挤出；`DesktopWindow` 已有同款）。
2. **互斥切换**：平时副本、peek 时正本；一个开关（`BETTERDESKTOP_DOCK_DESKTOP_LAYER=1`）控制，出问题一条命令回退。
   验收：peek 期间看到的是"没被变暗的 dock"；结束 peek 后副本回来。
3. **切 v2**：`ThumbnailWindow` 的格悬停从 `PreviewWindow` 改回 `WindowPeek.Begin(hwnd)`（点击 → 激活进入，`AttachThreadInput`/`SetForegroundWindow` 常规手段）。
   `PreviewWindow` **保留为开关**（`BETTERDESKTOP_DOCK_PEEK=v3`）——不骑墙，是给"下次真机撞墙"留一条命令级回退。

## 5. 风险（实施前先看）

| 风险 | 说明 | 缓解 |

## 6. 交接协议（用户 2026-09-14 追加的硬要求：无缝回落、不抽搐）

### 6.0 ⚠️ 先看这个：交接会**自激振荡**（用户指出的深层问题）

进入 peek 时，鼠标**必然停在缩略图上**，而缩略图浮层在 **dock 之外**。于是：

```
鼠标在浮层上 → 触发 peek → 透明化副本（含浮层）
  → 交接：藏副本、显正本
  → 但鼠标位置不在正本身上（正本只有底边那条 dock，浮层没跟着过去）
  → 正本没有"接住鼠标"的区域 → 悬停态丢失
  → peek 判定"鼠标离开" → End()
  → 副本回来 → 鼠标又落在副本的浮层上 → 再次 Begin()
  → 循环（反复抽搐）
```

**根因**：peek 的生命周期被"鼠标悬停在**我们的浮层**上"这个状态持有，而这层 UI 恰恰是 peek 要透明化的东西。**只要交接，就必须让浮层也一起交接过去并保持悬停命中**——否则必有振荡。

**结论：这不是"注意一下"就能解决的，而是原设计的结构性缺陷。** 下面 6.1 是"仍要交接"时的必做项；**6.6 给出的是不需要交接的解法（推荐）**。

### 6.6 推荐解法：**取消交接**——把 peek 从"悬停持有"改成"点击退出"

既然振荡来自"peek 由我们那层 UI 的悬停态持有"，就**不要让它持有**：

1. **悬停某个缩略图 → `WindowPeek.Begin(该窗口)`**（一次性动作，不是持续状态）。
2. **peek 保持**，直到：点击、按 Esc、或鼠标离开屏幕底部区域 —— **不因"鼠标不在浮层上"而结束**（我们调用的 API 本来就是我们自己控制 Enable/Disable，退出策略完全在我们手里）。
3. **peek 期间不需要我们的 UI**：亮出来的就是真窗口本身，用户**把鼠标移到那个真窗口上点一下**即激活进入（系统语义：点击被变暗的窗口会激活它并结束 peek）——这正是"置顶原生窗口"想要的效果。
4. ⇒ **没有交接、没有副本/正本切换、没有浮层跟随、没有振荡**；dock 与浮层在 peek 期间被变暗也无所谓（那一瞬间本来就不需要它们）。

**代价（必须承认）**：
- peek 期间无法在缩略图之间来回切换（浮层被变暗，看不清）；要换目标需先退出 peek。
- 因而 dock 也不需要上桌面层 —— **第 3 节的"正本/副本双实例"可以整体取消**（这是好事：少一个窗口、少一套生命周期、少一份内存）。

> 待用户确认走 6.6 后，第 3/4 节的双实例方案作废，改为"改 `WindowPeek` 的退出策略 + `ThumbnailWindow` 接线"。

### 6.1 两个必须做对的点（若仍走"交接"路线）

**正常路径**：从**副本**发起 → DWM 透明化所有顶层窗口（含副本）→ 显示与操作**回落到正本** → 正本要无缝接住。

### 6.1 两个必须做对的点（否则"回落到正本"是假的）

1. **正本必须预建 + 预热，绝不在切换时创建。**
   切换路径上任何"创建窗口 / 加载图标 / 重建列表"都会造成可见的抽搐（WPF 首帧 + 布局 + 图标解码）。
   → 正本**常驻存在**（不可见、但已 `UpdateLayout` 完成、已订阅同一组单源服务、图标已在 `IAppIconService` 缓存里热着）；
   → 切换只允许做：`ShowWindow`/`Visibility`、命中属性切换、必要时**一次**同步布局。
2. **peek 期间必须主动隐藏副本，不能只靠 DWM 把它变暗。**
   被透明化的副本**仍是顶层窗口**——它仍可能是鼠标命中的目标 → 点击落不到正本 → "回落到正本"只在显示层面成立、操作层面是假的。
   → 我们发起的 peek，我们**知道开始时刻**，就在那一刻自己把副本藏掉（`IsHitTestVisible=false` + 隐藏）。

### 6.2 切换顺序（两者几何/内容完全一致 ⇒ 允许一帧重叠，视觉等价）

```
悬停浮层格
  → ① 正本就位（已在原位、已同步、已预热）
  → ② WindowPeek.Begin(目标窗口)        // 顶层窗口被透明化
  → ③ 显示正本 + 隐藏副本（同一帧内完成）
  → ④ 点击正本 → 激活进入；移开 → WindowPeek.End()
  → ⑤ 隐藏正本 + 显示副本（同一帧内完成）
```

先显正本再隐副本：因为两者重叠且内容一致，即使存在一帧重叠也**视觉等价**；反过来（先隐后显）会有一帧"dock 消失" → 就是抽搐。

### 6.3 切换路径上的禁令

- ❌ 建窗、加载图标、`ApplyFilter` / `RebuildRunningPanel` 之类全量重建
- ❌ 分配敏感操作（`shell-dock-tests` 有分配门 `ReflectionRtbAllocationTests.FullDockRebuild_RtbAllocation_UnderGate` —— 正本不得在切换时触发重建，否则既卡顿又可能踩门）
- ✅ 只允许：可见性 / 命中 / 一次同步布局

### 6.4 验收（真机，必须全部过）

1. peek 前后切换**看不出跳变**（不闪、不抖、不位移）
2. 切换瞬间**不丢帧、不闪白**
3. peek 期间**能点正本**（显示与操作都真的在正本上）
4. 结束 peek 后副本无缝回来
5. **连续快速进出 10 次**不抖、不卡、不残留（两个都可见 / 两个都不可见 都不允许）

### 6.5 兜底

任一步超时或失败 → **放弃切换，维持"只显示副本"**（宁可 dock 在 peek 里被变暗，也不允许出现"两个都不可见"或"两个都可见"的坏态）。
