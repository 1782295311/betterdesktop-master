## 二、依赖关系

```
热键注册表（1）
  └─ 截图热键登记（2 的入口）
  └─ 侧板两态窗口能力（1 自身）
OCR 引擎字段与动词（3）
  └─ 截图后的"识别"动作（2 的工具条）
  └─ 历史图片补做识别（3 自身）
包标识 + userNotificationListener（4）
  └─ 系统通知进岛（5 的消息源）
活动服务 IActivityService（5）
  └─ 通知（4）/ 截图（2）/ OCR（3）的呈现面
剪贴板按序粘贴推送面（5 依赖，改 shell-clipboard-ipc）
菜单栏中置列（5 依赖，改 shell-menu-bar）
自渲染层与液体动效（6）→ 被 5 依赖；依赖 D3D11/DComp/D2D 互操作库
```

无依赖的边：截图（2）除热键登记外不依赖任何新件；OCR（3）除引擎字段外不依赖截图；渲染层（6）与热键、通知、OCR 之间没有依赖。

## 三、开工顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| P0-1 | OCR 的引擎侧改动：`ocr_text` 字段 + `set_ocr_text` + `keyword_hits` 覆盖（文档 3 §3.1） | 独立可测、不碰活跃链路，且是截图与 OCR 共同的上游 |
| P0-2 | 热键注册表服务与冲突治理（文档 1 §2-§7） | 侧板与截图热键的共同地基；顺带修掉现有热键冲突不可见的隐患 |
| P0-3 | 点击穿透两态窗口原语 + 右 Alt 门控（文档 1 §8） | 侧板交互的先决条件 |
| P1 | 截图最小闭环（采集 → 落盘 → 写剪贴板 → 历史）→ 覆盖层 → 编辑器 → 贴图（文档 2 §5） | 用户可感知价值最大的一条链 |
| P2 | OCR 三层引擎与后处理 + 面板/截图工具条接线 + 准确率门禁（文档 3 §2-§8） | 依赖 P0-1 与截图产物 |
| P3 | 灵动岛：活动服务与中置列（文档 5 §3-§6）+ **自渲染层与液体动效（文档 6）** + 三个既有源接线 + 按序粘贴预览 | 三个消息源已就绪，接线成本低；动效成本集中在自渲染层，需单独排期 |
| P4 | 系统通知采集（文档 4）——**先打通包标识与签名链路** | 该前置是独立工程（稀疏包 + 签名），不要放在岛之后做 |
| P5 | 热键侧板 UI 与既有热键迁移（文档 1 §9-§10） | 依赖 P0-2/P0-3，且迁移要逐项回归 |
| P6 | 商用配套：自动更新与签名、多显示器全覆盖、性能与准确率门禁进 CI、一键诊断包 | 与既有性能审计结论衔接 |

## 五、需要在机制注册表登记的行

按 `docs/MECHANISMS.md` 的"登记即承诺"流程，随实现同步新增：

| 关注点 | 选用机制 | 禁止 |
|---|---|---|
| 屏幕采集 | 单一采集服务 + 后端优先级链（WGC → DXGI → BitBlt） | 各包自建 BitBlt、第二套采集封装 |
| 文字识别 | 单一 `IOcrService` + 引擎优先级链（in-box → ONNX → NPU） | 各消费方自接引擎、云端识别 |
| 活动呈现 | 单一活动服务 + 显式仲裁表 | 各表面自建消息队列、直接抢 UI |
| 热键 | 单一注册表（中心窗口 + 单钩子查表） | 各包自行 `RegisterHotKey`、钩子内硬编码键位 |
| 点击穿透两态 | shell-core 单一窗口原语 | 各窗口自行改扩展样式 |
| 自绘动画表面 | 唯一自渲染层（无重定向位图窗口 + DirectComposition），只服务灵动岛 | 其他包再开一套自绘、把动画放回分层窗口的软件路径 |
| 系统通知 | 单一读取契约 + 稀疏包能力 | 各包自行申请权限、第二套通知读取 |

## 六、待拍板（会改变实现细节，不改变结构）

1. 侧板门控键：默认右 Alt（若用户会输入 AltGr 字符则改右 Ctrl）。
2. 截图入口：独立入口面 exe（当前设计）还是并入剪贴板面板进程。
3. 灵动岛位置：菜单栏中置（当前设计）还是独立悬浮胶囊。
4. OCR 结果落点：挂同一图片条目（当前设计）还是另存一条文本条目。
5. 是否打包 PP-OCR ONNX 模型（体积 +20–40 MB 换中文精度）。
6. 是否引入 D3D11/DComp/D2D 互操作库（同时影响截图后端与岛的渲染层）：推荐 Vortice.Windows（MIT），不引入则手写 COM 互操作，结果等价、维护成本高得多，且岛的液体动效工期显著拉长。
7. 菜单栏改造分期（见动效规格 §2.2）：是否按 S1（度量契约，随岛一起做）→ S2（声明式条目模型）起步，S3/S4 视收益再定。

## 七、与既有纪律的衔接

- 归属：按 [../2026-09-11-resident-architecture.md](../2026-09-11-resident-architecture.md)——能力（采集、识别、通知读取、热键注册表）常驻或随其宿主；视觉表面（截图覆盖层、岛、侧板）留壳。
- 失败语义：全部走 `docs/runtime-health.md` 的 fail-visible 与"降级必须可见"。
- 跨语言：截图采集与识别留在 C#（WinRT 与 NPU 档可用性优先），引擎只做数据面；判据见 [../cross-language/原生重写候选评估.md](../cross-language/原生重写候选评估.md)。
- 性能：截图唤出、动画帧预算、识别耗时、扫描耗时统一进基准工程与门禁，基线冻结后按 [../product-quality.md](../product-quality.md) 的"回归超阈值即红"执行。
