# 原生重写候选评估（跨语言落点判定）

> 地位：跨语言体系的功能筛选输入——判定哪些能力值得离开宿主进程、或离开托管运行时。本文只给候选与判据，不构成实施授权；单个候选的实施须按 [计划-跨语言插件体系.md](计划-跨语言插件体系.md) 的协议与生命周期规则另起计划。
> 证据基准：2026-09-12 工作树（本仓库尚无 commit）。内核层测量引自 [../performance/diagnose-2026-09-07.md](../performance/diagnose-2026-09-07.md)；进程归属判定见 [../2026-09-11-resident-architecture.md](../2026-09-11-resident-architecture.md)；崩溃隔离分级见 [../MECHANISMS.md](../MECHANISMS.md) M14 与 [../pluginization.md](../pluginization.md)。
> 核验状态：2026-09-13 对 §二 与 §4.1–§4.4 的全部行号引用逐条回源码取证。已修正 4 处失准：§二 非托管 DLL 数（8→9）、§4.2 兜底扫描触发语义（"未命中才兜底"→并行且始终合并）、§4.3 应用源锚点（`:48` UWP 分支 → `:196` 通用路径）、§4.4 两条论断（IME 与 SMTC 采集均已迁原生，非"仍在托管"）。连带更正 1 处上游文档：`packages/shell/shell-search/README.md` 的「降级为空」（实为降级为文件系统扫描）。

## 一、判定口径

原生化收益只有两个可验证来源（离开进程 / 离开 GC 堆），但放行与否要四条边界一起看。任一维度落在右列即应否决：

| 维度 | 该原生化 | 不该原生化 | 误判的典型表现 |
|---|---|---|---|
| 是否必须离开宿主进程 | 执行第三方不可信代码（in-proc COM handler、注入 DLL、外部 exe） | 只调用稳定 Win32 API | 换个独立进程即可，与语言无关 |
| 是否必须离开 GC 堆 | 百万级条目、GB 级扫描、常驻大索引、逐帧媒体数据 | 百级条目、一次性任务 | 堆压力不足以抵消跨语言类型/生命周期成本 |
| 热路径是否高频消费 | 被 UI 线程或共享进程高频消费（每帧、每次输入、每次查询） | 低频能力 | 只需下沉独立进程，无需换语言 |
| 切面是否足够窄 | 一个函数或一个数据结构 | 横跨多模块的宽切面 | 跨语言边界沿切面蔓延，成本随宽度增长 |

两条补充纪律：

- **语言本身不是收益来源**——剪贴板审计（工作区根 `剪贴板性能审计-瓶颈定位与语言选型.html`，仓库外）的结论是六成以上痛点为设计层、C# 内即可修复，该结论对本仓其余模块同样成立。
- **证据级别必须标注**——沿用 [../performance/diagnose-2026-09-07.md](../performance/diagnose-2026-09-07.md) 的取证口径：`SOURCE`（源码/文档可核）、`RUNTIME_ARTIFACT`（有运行测量产物）、`EVIDENCE_REQUIRED`（仅静态推断）。`SOURCE` 级候选可进候选表，但不足以支撑排序——"收益最大"必须由测量背书。

## 三、候选总表

| 候选 | 目标形态 | 语言收益 | 解决的问题 | 证据级别 | 前置依赖 | 结论 |
|---|---|---|---|---|---|---|
| 右键菜单第三方 COM 执行 | 进程外 broker | 边际（同一 DLL 可兼顾 in-proc 扩展） | 宿主进程被第三方 handler 打崩 | `RUNTIME_ARTIFACT`（两次真机 AV，见 §4.1） | 跨语言进程骨架（`ExternalPluginAdapter`）；与免宿主 B 路共用实现 | 优先级最高 |

排序说明：优先级不由"语言收益"单独决定——4.1 的收益是**消除崩溃面**（失败域不可协商），4.2+4.3 的收益是**吞吐与内存**（可测量、可排期）；这正是 4.1 虽语言收益"边际"仍排第一的原因。反过来，4.2 虽标注"收益最大"，当前证据仅为静态自述，进入实施前须先补一次全量扫描耗时基线（见 §七 第 7 条）。

## 四、候选详述

### 4.1 右键菜单第三方 COM 执行

> **2026-09-14 实施状态：第一、二、三步（宿主侧）已落地。** 归因 = `HandlerCrashGuard`（inflight 标记 / broker 退出码 → 连续计数），执行 = `HandlerCrashBreaker`（达阈值经既有 `MenuManagerService.Toggle` 自动停用，写前备份、可逆），进程边界 = `MenuBrokerClient` + `BetterDesktopMenuBroker.exe`（stdio JSON，非 0 退出码即"handler 搞死了 broker"）。broker 与免宿主 B 路同一 CMake 工程、同一份 `JsonLite`/`MenuModel`/`Launcher` 源码，**两个产物**（见 §七 第 3 条）。`ShellMenuInterop` 按 CLSID 直查**只有 broker 一份实现**——宿主侧 in-proc 副本（含 4 个 COM 接口与 HMENU 遍历）在同日查重中删除：它与 broker 是同一件事的两份实现，且宿主那份就是崩溃面；本项验收写的是"降级为空菜单"而非"回宿主进程内重跑"。broker 不可用时返回**一条可见说明项**（fail-visible），不静默返回空菜单。仍不在范围内：`NativeMenuPopup` 的系统聚合菜单（HMENU 不能跨进程，且归属不到具体 CLSID）。
>
> **证据归因更正（2026-09-14）**：下文"缺口代价（已付）"两条真机 AV 均为**自因**——一次是宿主 STA 线程缺 `OleInitialize`（`StaComWorker.cs:56-60`），一次是 `IContextMenu`/`IShellExtInit` 的 IID 写反（`ShellMenuInterop.cs:69-72`，注释自记"当时 OleInitialize 归因不完整"）。真机证据支持的是"宿主 COM 初始化纪律"，**不支持**"第三方 handler 已打崩宿主"。故本项优先级理由应改为：预览入口成本最低 + 熔断当时完全缺失，而非"已付代价"。
>
> **入口补漏（2026-09-14）**：除右键外还有第二个、更主动的入口——设置中心「菜单管理」展开某 ShellEx 扩展详情即经 `MenuManagerSection.cs:652-658` → `ShellExMenuPreview` → `ShellMenuInterop.Query`，在宿主内实例化**任意已注册 CLSID**；其 5 秒超时（`ShellExMenuPreview.cs:22,30`）挡得住托管等待、挡不住 native AV。本次该路径已整体外置。

**现状（实施前基线，2026-09-14 之前）**：第三方 shell 扩展的查询与执行发生在宿主进程内：`ShellMenuInterop.cs:282-297` 以 `Type.GetTypeFromCLSID` 加 `Activator.CreateInstance` 加载 in-proc handler，`NativeMenuPopup.cs:218-232` 经 `GetUIObjectOf(IContextMenu)` 绑定系统菜单。代码注释已明示隔离缺口——「COM handler 在进程内运行，SEH 级崩溃无法托管隔离」（`packages/shell/shell-context-menu/Services/ShellMenuInterop.cs:24-25`）；`StaComWorker` 只提供 STA 线程，不提供进程边界。

**缺口代价（已付）**：

- 真机 AV 两次记录（`packages/shell/shell-context-menu/Services/StaComWorker.cs:56-60`，`QueryBackground → QueryContextMenu → coreclr 0xc0000005`，诱因为宿主线程缺 `OleInitialize`，已修）——崩溃发生在宿主进程内，注释登记的兜底是「host 有 watchdog/recovery」（`ShellMenuInterop.cs:24-25`），即**进程级重启而非插件级隔离**。
- 现有缓解手段都不足以覆盖：per-handler 屏蔽依赖日志定位后人工配置（`packages/shell/shell-context-menu/README.md` Known Limitations），无自动熔断；而 `pluginization.md` §四 的「连续崩溃 3 次 → 熔断 + 回退默认」也够不着——第三方 COM handler 不是 Cordis 插件，跑在 `PluginGuard`（§三 L0 的 fiber 边界）之外，崩溃根本不会计到任何插件的账上。

**为什么进程边界是唯一解（与语言无关）**：C# 独立进程同样能隔离，`pluginization.md` §三 的 L1（进程外 worker + IPC）就是为「重资源 / 不可信插件」定义的级位。选 C++ 的额外收益只有两条：

1. 同一份代码可同时承担 explorer 内 in-proc 扩展与进程外 broker，不必维护两套 handler 调用链；
2. 绕开托管 / 非托管 COM 互操作的指针级错位——`CMINVOKECOMMANDINFOEX` 布局错位、`HandleMenuMsg2` 的 `plResult` 空指针两处 AV 均属此类（`packages/shell/shell-context-menu/README.md` §4 红线 3）。

**与 B 路的复用边界（2026-09-14 已定为「两个产物、一份源码」）**：与 [../plans/2026-09-11-hostless-shell-shortcuts-com-extension.md](../plans/2026-09-11-hostless-shell-shortcuts-com-extension.md) 的 B 路共用实现，不另起一套。B 路 `BetterDesktopShellMenu.dll` **必须** in-proc（explorer/dllhost 加载、`.def` 导出 `DllGetClassObject`、注册表或 MSIX 稀疏包注册），broker **必须**独立 EXE（进程边界即其存在意义），两者同属一个 CMake 工程、共享 `JsonLite`/`MenuModel`/`Launcher`。**"同一产物"对第三方 handler 技术上不成立**：第三方 in-proc CLSID 的加载进程由 COM 决定，要让它跑在我们指定的进程里，只能给第三方 CLSID 写 `AppID` + `DllSurrogate` —— 那是全局注册表污染、影响其他应用，不可接受。

**切面与验收**：切面 = 一张「场景 → handler 列表 → 菜单项树 → 命令调用」的数据结构 + 一次跨进程调用，可窄到不触及宿主 UI 代码（符合 §一 维度 4）。验收不变量：broker 进程被杀后宿主菜单仍可用（降级为系统菜单或空菜单，不得静默无菜单），熔断状态在设置中心「组件管理」可见。

### 4.2 文件 / 应用 / 图标合并索引

文件搜索不建索引：`FileSearchProvider.cs:49-92` 调用系统 Windows Search（`SearchManager` CLSID → `SystemIndex` → `ISearchQueryHelper` → ADODB 执行 SQL）。兜底**不是"索引未命中才触发"，而是与索引查询并行执行、结果始终合并**（`packages/shell/shell-search/Services/FileSearchProvider.cs:39-42,190-227`；深度 2、1.5 秒超时、上限 20 条）——注释明示原因：索引会命中同名子串的无关文件（搜 `maa` 命中 Python 库 `CMAA`）占坑，只在空结果时兜底将永不触发。兜底扫描根 = 用户 下载/桌面/文档 + 各固定盘根一级子目录（跳过 `Windows`/`Program Files` 等大目录剪枝，覆盖 `D:\迅雷下载` 这类未索引中文目录）。全仓无 USN Journal / MFT / Everything SDK 代码。包 README 记录「不含 `ScanAllPrograms`（磁盘深度遍历无缓存，逐键调用会卡输入）」（`packages/shell/shell-search/README.md`）；同页原写「服务禁用 / 未索引时降级为空」与代码不符（代码实际降级为文件系统扫描），已于 2026-09-13 更正该 README。应用源为全量扫描：开始菜单全递归（`AppSourceService.cs:452` 的 `SearchOption.AllDirectories`，无深度上限）、注册表三视图遍历（三视图定义在 `:168-173`＝HKCU + HKLM + WOW6432Node，遍历体 `:175-247`）、全程序盘点递归深度 3（`:750-838`，`maxDepth: 3`），DESIGN 自记「`ScanAllPrograms` 大盘点增量缓存细则（当前全量扫 + 内存缓存）」（`packages/shell/shell-app-source/DESIGN.md:162`）。窗口追踪每次 `GetRunningApps` 重建路径索引（`packages/shell/shell-window-tracker/README.md`）。

三个消费者共享同一份「磁盘上有哪些 exe、文件、图标」的事实，应在一次原生遍历中产出并常驻。Rust 的结构性优势在此成立：零 GC、内存映射、可常驻 GB 级索引且无堆放大；C# 维持常驻索引会带来 GC 压力与大堆。消费者保持 C#，只经 IPC 查询。

### 4.3 图标与缩略图批量提取

图标提取分散在四处、**四套互不复用的实现**：

| 消费方 | 锚点 | 实际调用链 |
|---|---|---|
| 应用源 | `Win32ShellIconService.cs:196`（Win32 通用路径）/ `:47-49`（UWP 分支） | ManagedShell `IconHelper.GetIconByFilename`（48px，UWP 用 `IShellItemImageFactory` 44px）；256 高清经 `HighResIconExtractor.cs:53` 动态解析 `SHExtractIconsW` 私有导出 |
| 菜单栏 | `ProcessAppInfo.cs:175` | `System.Drawing.Icon.ExtractAssociatedIcon`（按 PID，60s TTL 缓存） |
| 右键菜单 | `MenuItemIconCache.cs:146` | `ExtractIconEx`（小图标优先，行高 16px，进程级缓存） |
| 剪贴板 | `FileIconCache.cs:58` | `SHGetFileInfoW` + `SHGFI_LARGEICON`（按扩展名缓存） |

四处各自持有缓存与解码路径（`ProcessAppInfo` 与 `MenuItemIconCache` 返回 `ImageSource`，`FileIconCache` 冻结后跨线程绑定），仅应用源有 `PrefetchAsync` 批量预热入口，其余按需逐项调用。与 4.2 合并为同一索引服务的输出面（原生直出字节，C# 只做 `BitmapSource` 显示），不单独立项。

### 4.4 状态采集剩余部分

重负载采集已在 C++ DLL（见第二节）。**本项的两条论断在 2026-09-13 核验中均被推翻——它们描述的迁移已经完成**：

- **IME 已迁原生**：按键序列模拟落在 `Native/src/ime_core.cpp`（导出 `Ime_CycleOnce` / `Ime_SimulateCtrlShift`；Win+Space 80/60/60/150ms、Ctrl+Shift 50/50/50ms），经 `Native/ImeCoreNative.cs:17-18` 加载，`KeyboardLayoutInterop.cs:779-788` **优先走 `ImeCore.dll`**；托管 `keybd_event` + `Thread.Sleep` 只是 DLL 缺失时的回退路径，且它们是**按键定序间隔而非重试循环**（"重试"是 `diagnose-2026-09-07.md` §3.6 的推测措辞）。
- **SMTC 采集与命令已迁原生**：`MediaPlayerCore.cs:2-5` 自述「会话采集与命令执行已迁入原生 MediaCore.dll……本类保留为包内编排层」，`GetSnapshotAsync` / `SendCommandAsync` 均经 `MediaCoreNative`。残留托管的只有缩略图流引用桥 `NativeThumbnailReference : IRandomAccessStreamReference`（`:219-246`，字节仍取自 `MediaCoreNative.GetThumbnailBytes`），因为 UI 层需要 WinRT 流契约。

因此 4.4 由「待迁移」降级为**收尾项**：真正还能原生的只剩 IME 编排的其余部分（TSF `ActivateProfile`、`WM_INPUTLANGCHANGEREQUEST`、Preload 注册表写入）与那层缩略图流托管桥，收益低。并入既有 `Native/src` 与 `natives/` 分发链、不新开语言工程的结论不变，但**不应再按"收益中等"排期**。

### 4.5 被降级的候选：窗口追踪 `GetRunningApps`

`GetRunningApps` 每次调用都重新 `ScanStartMenu` + `ScanInstalledApps` 构建路径索引，服务内无缓存（`packages/shell/shell-window-tracker/README.md` Known Limitations）；调用点 `Services/WindowTrackerService.cs:65,126,140,161,212`，其中 `IsRunning` / `GetWindowsOfApp` / `GetWindowTitle` 都会间接触发一次全量重建。

缺陷在**设计层**（未缓存），不在运行时：C# 内加一层路径索引缓存即可消除全部重复扫描，原生化零收益。登记此项是为了与 §三 的表行一一对应——**「不原生化」不等于「不用改」**。

## 五、明确不原生化

| 模块 | 理由 | 证据 | 对应判据 |
|---|---|---|---|
| 全部 WPF 视觉层（Dock / 菜单栏 / 弹层 / 设置中心） | 重写代价高于收益；`RenderTargetBitmap` 类效果属 WPF 渲染管线，脱离 WPF 等于自绘整窗 | [../performance/diagnose-2026-09-07.md](../performance/diagnose-2026-09-07.md) §3.4（真实启动瓶颈候选 = WPF UI 线程串行化，即视觉层正是成本中心） | 维度 4（切面极宽） |
| 窗口管理 / 注册表 / COM 编排 / AppBar / 托盘接管 | 与系统 API 一一对应，换语言零收益 | 判据本身 | 维度 1（不离开进程） |
| shell-dock 的 tick 裁决 | 已由 `DockTickPolicy` 双档自适应降频（快 60ms / 慢 250ms），空闲 1h tick 数 60 000 → ≤14 400 | `packages/shell/shell-dock/DockTickPolicy.cs:12-13`（A/B 门槛由 `DockTickPolicyTests` 守护） | 维度 3（已降频，热路径不复成立） |
| shell-calendar | 节气为单年 24 次牛顿迭代（每节气 ≤8 次迭代）且按年缓存，量级在微秒 | `packages/shell/shell-calendar/Services/SolarTermCalculator.cs:62-63`、`SolarTermProvider.cs:9` | 维度 2（非大索引） |

兜底规则：凡理由为「数据量小 / 换语言零收益」的行都是**有时效的**——若数据量数量级发生变化（例如 recent 列表升到万级、通知历史长期驻留），必须重新过 §一 四条判据。本表不是永久豁免名单。

## 六、承载方式

候选一律走既有两档，不新建框架：能力下沉用 `BetterDesktop.Agent.exe` 常驻装配（[../2026-09-11-resident-architecture.md](../2026-09-11-resident-architecture.md)）；跨语言进程用 `ExternalPluginAdapter` 加 JSON-RPC 协议（[计划-跨语言插件体系.md](计划-跨语言插件体系.md)）。语言选择判据：必须注入 explorer 的能力只能用 C++；其余以 Rust 为先（内存安全且无 GC）。

| 候选 | 承载 | 语言 | 通道 | 数据面 | 生命周期归属 |
|---|---|---|---|---|---|
| 4.1 第三方 COM broker | 跨语言进程（**已落地**：stdio 一次性调用；`ExternalPluginAdapter` 仅作生命周期归属） | C++（与免宿主 B 路**同工程两产物**） | stdio JSON 一进一出 | 菜单描述 JSON + 命令调用 | 按需一次性；**非 0 退出码即当场归因**，连续 3 次自动停用（2026-09-14 已落地） |
| 4.2 合并索引 + 4.3 图标提取 | 常驻进程（归属未决，见下） | Rust 优先 | 命名管道 + 命名共享内存（图标字节） | 索引结果集 + 原始字节 | 常驻；须与壳生命周期解耦 |
| 4.4 IME / SMTC | 并入既有 C++ DLL | C++ | 既有 DLL 导出（`natives/` 分发链） | 结构体 | 随 `shell-status` 装配 |
| （先例）剪贴板引擎 | 独立 Rust 进程 + 命名管道 | Rust | 命名管道 | 剪贴板条目 | 独立于宿主（[../plans/2026-09-11-clipboard-engine-rust-ipc.md](../plans/2026-09-11-clipboard-engine-rust-ipc.md)） |

**关于 4.2 的承载归属（未决）**：`BetterDesktop.Agent.exe` 本身是 C# 宿主（[../2026-09-11-resident-architecture.md](../2026-09-11-resident-architecture.md) §三），索引服务若是 Rust 进程，只可能是两种形态之一——Agent 的**子进程**（由 Agent 拉起并纳管，复用其健康上报），或与剪贴板引擎同款的**独立常驻进程**（Agent/壳仅作消费者）。后者与「壳退出后继续工作」的原则更一致，但要自建单实例与健康上报，见 §七 第 5 条。

**大块数据前置**：图标与缩略图字节不适合走 base64（协议草案 §3 #1 限 64KB 且拒绝超限），必须等 Phase 3 的命名共享内存（[计划-跨语言插件体系.md](计划-跨语言插件体系.md) §7）。在 Phase 3 落地前，索引服务只返回「图标可用」的元数据、字节仍由 C# 侧按需提取——即 **4.3 的收益在 Phase 3 之前无法兑现**，这是 4.2/4.3 不能拆成两个独立立项的直接原因。

## 七、实施前必须回答

下列问题在对应候选进入实施计划前必须逐条有答案——缺项即视为计划未就绪（与 [计划-跨语言插件体系.md](计划-跨语言插件体系.md) §12 总验收同为立项门槛）。

1. 4.2 的索引服务与 `shell-app-source` 谁是「已安装应用」的权威源，避免双份事实。
2. 索引范围与增量策略，含 MFT / USN Journal 的可用性与权限边界。
3. ✅ 4.1 的 broker 与 B 路 in-proc DLL：**两个产物、一份源码**（同一 CMake 工程共享 `JsonLite`/`MenuModel`/`Launcher`；DLL 必须 in-proc、broker 必须独立 EXE；"同一产物"只能靠给第三方 CLSID 写 `AppID`/`DllSurrogate`，属全局注册表污染）。2026-09-14 已按此实施。
4. 索引服务的常驻内存上限及其与 `IResourceGovernor` 的关系。
5. 4.2 索引服务是 `Agent` 的子进程，还是与剪贴板引擎同款的独立常驻进程？影响单实例、健康上报与「壳退出后继续工作」的语义（见 §六）。
6. 索引不可用 / 未就绪时消费者的降级形态：回退到 Windows Search + 现有全量扫描，还是显式提示「索引未就绪」？降级必须可见，不得静默（`docs/runtime-health.md` fail-closed 纪律）。
7. 现有论断的证据级别为 `SOURCE`（README/DESIGN 自述），实施前是否先补一次全量扫描耗时基线（`ScanAllPrograms` 全程序盘点与 `FileSearchProvider` 递归兜底路径）？否则「收益最大」无同合同证据支撑，不满足 §一 的证据纪律。
