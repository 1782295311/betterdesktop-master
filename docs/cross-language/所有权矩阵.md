# 跨语言所有权矩阵

> 本文回答**静态脚本查不出的那一类问题**：同一件事是不是在 Rust 和 C# 里各写了一份。
>
> 静态体检能查"谁调了 `Process.Start`""谁写了 settings.json"；查不出"**同一件事有两个实现者**"——
> 因为两侧的符号名、文件布局、调用形态都不同，正则匹配不上。这一层只能用**矩阵**查。
>
> 依据：`docs/architecture/2026-09-20-current-architecture.md` §二（六层 + 单向依赖）、
> `docs/plans/2026-09-18-on-demand-core-architecture.md`（S0.5…S8 收敛步骤）、
> `scripts/manifests/architecture-allowlist.json`（机器校验的登记表）。
> 原料：`pwsh -File scripts/health-check.ps1 -Only A8`（概念 × 语言 命中文件数）。
> 最后核实：2026-09-20。

---

## 一、判据（三条，缺一不可）

1. **每个功能只能有一个所有者**。"所有者"= 唯一决策者（唯一写者 / 唯一生命期持有者）。
2. **其他语言只能"请求"，不能"实现"**。请求 = 经控制管道 / 事件 / 协议说一句；实现 = 自己拉起、自己改状态。
3. **出现两个语言都标"所有者" = 重复，必须收敛**。

矩阵的价值不在"填得多全"，在**逼出第 3 条**：双所有者不会让任何一次编译失败，
只会让行为取决于"谁先跑"—— 症状是随机的，根因是结构性的。

---

## 二、填充方法（给 AI 的提示词）

```text
请扫描本仓库，对每个功能列出所有实现位置（文件:行号），
然后判断哪个是"所有者"（唯一决策者），哪些是"重复"（应删除）。
输出表格：功能 | 实现位置（按语言分列） | 所有者 | 重复项 | 收敛步骤。
判据：单所有者；其他语言只能请求不能实现；两个语言都标所有者 = 重复。
```

填完后**人工核对三问**：

- ① 有没有功能**没有**所有者？—— 没人决策 ⇒ 行为取决于"谁先跑"，必失稳。
- ② 有没有功能**有两个**所有者？—— 重复实现，必须收敛。
- ③ 有没有功能的"所有者"**放错了层**？—— 例："必须活过壳退出"的能力放在壳里（壳一退就没了）。

## 四、人工核对三问（本轮结论）

**① 有没有功能没有所有者？**
没有。每个功能都能指出唯一决策者。唯一"待人工确认"的是**桌面图标独占**（最后一行）—— 它不是"没有所有者"，是"两个所有者共存且边界靠约定"，需要一次显式拍板。

**② 有没有功能有两个所有者？**
有，但**全部是已登记的过渡期重复**，且每一条都有收敛步骤（S5/S6/S7）：

| 重复项 | 收敛步骤 | 机器校验位置 |
|---|---|---|
| C# 托盘（`tray/`） | S5 | allowlist `lifecycle-owner` 的 `tray\ProcessBridge.cs` / `tray\TrayApplicationContext.cs` |
| 宿主三条 Ensure（`host/Bootstrap.cs`） | S6 | 同上 |
| ~~壳内引擎启动器（`shell-index-ipc/`、`shell-clipboard-ipc/`）~~ | **✅ 已收敛（2026-09-20）** | allowlist 条目**已随现实消失而删除**（棘轮收缩）；门禁从 16 命中降到 13 |
| CLI headless 拉起 / 直写配置 | S7 | allowlist `lifecycle-owner` + `settings-writer`（`HeadlessExecutor` 的 DesktopControl/Host/桌面控制菜单三条已收敛，仅剩 `--toggle-key` 一条带**动态参数**的拉起点无法用静态组件表表达） |
| `host/HostWatchdog.cs` | S4-4 / S6 | 旧守护者，STATUS §五 B4 |
| 两条非 core 命令通道服务端 | S6 / S7 | 尚未登记（见"缺口"） |

**③ 有没有功能的"所有者"放错了层？**
没有发现放错层的。唯一值得标注的是 `core/src/shellmenu.rs`：它**触发**重建但不写内容 —— 这不是放错层，是刻意的分层（core 不持业务数据）。

## 五、本矩阵查出的缺口（尚未有门禁）

| 缺口 | 说明 | 建议 |
|---|---|---|
| **规则口径写窄 → 所有者隐形（2026-09-20 已修）** | `lifecycle-owner` 的 exe 名只匹配"两段名"，`BetterDesktop.Index.Engine.exe`（三段）等**全隐形**，于是 `shell-index-ipc/IndexEngineLauncher.cs` 这个真实第二所有者从未被看见（真机探针抓到：其拉起的实例父进程不是 core） | 已修正则允许多段；**下一个方向已落地**：改由 B5 直接对账 `core/components.json` 的组件名，不再靠正则猜名字 |
| 命令通道服务端无归属门禁 | "终态只允许 core 持服务端"目前**没有任何门禁**；两条非 core 服务端也没登记进棘轮 | 先拍板"数据面引擎的管道算不算命令通道"，再加规则 + 登记 |
| 引擎管道 ACL 空缺 | `engine` / `engine-index` 的 `CreateNamedPipeW` 传 `None`（系统默认 DACL），与 core 的显式 ACL 不同档 | 决定"接受（登记进 known-exceptions）"或"补齐 ACL" |
| 桌面图标独占语义未拍板 | 见上表最后一行 | 一次显式决策，落进 `docs/architecture/` |
| `--toggle-key` 的动态参数 | 组件表的 `args` 是静态串，表达不了"参数由调用方决定"的拉起点（`BetterDesktop.Cli/HeadlessExecutor.LaunchDesktopServiceToggle`） | 要么给 core 加"带参启动"verb（会开一个注入面，需先定白名单），要么让该开关走"写设置 → core 的 gate/auto_start 自动落地" |

## 五之二、2026-09-20 收敛轮次（core 作为唯一生命周期所有者）

**触发**：真机探针发现 `BetterDesktop.Index.Engine.exe` 的父进程不是 core ⇒ 追出壳侧两个引擎启动器
（`shell-index-ipc` / `shell-clipboard-ipc`）自己 `Process.Start` + `Kill` + 按进程名判活。

**做法**：新增 `packages/kernel/kernel/Core/CoreComponents.cs` 作为**壳侧唯一的组件启停入口**，
把"谁拉起、在哪找 exe、开关关没关、要不要重复拉起"四件事全部交回 core（`start/stop/toggle` 控制管道）。
kernel 是零依赖契约层 ⇒ 任何壳包引用它都不产生环（`surface → kernel` 合法）。

**收敛清单**：

| 位置 | 收敛前 | 收敛后 |
|---|---|---|
| `shell-index-ipc/IndexEngineLauncher` | 自己定位 exe + `StartDetached` + 按进程名判活 | `CoreComponents.Start("index-engine")` |
| `shell-clipboard-ipc/ClipboardEngineLauncher` | 同上，且自己 `Kill` + `WaitForExit` + 读 `deployment.json` 找安装根 | `CoreComponents` 的 start/stop/toggle/status |
| `shell-clipboard-panel/EngineProber` | 转发"定位 + 拉起" | 转发"请 core 确保在跑" |
| `shell-desktop-control/DesktopControlEntry.EnsureServiceStarted` | 用 `Environment.ProcessPath` 把自己再拉一份 | `CoreComponents.Start("desktop")` |
| `BetterDesktop.Cli/HeadlessExecutor`（桌面控制菜单 / 桌面服务 / 宿主 三条） | 自己定位 + `Process.Start` | `CoreComponents.Start("desktop-controls" / "desktop" / "shell")` |

**可达性补缺**（`core/components.json` 7 → 9 个组件）：

- 新增 `desktop-controls`（`--desktop-controls`，type=tool）：菜单此前不在表里，只能由 CLI 拉起 ⇒ core 既看不见也管不着；
  参数写进表里还顺手消掉"漏传参数会退化成拉起常驻服务"这个真机坑。
- 新增 `clipboard-panel-open`（`--open`，type=tool）：把"装配入口"与"打开面板"分成两个组件 ——
  面板 exe 是单实例，`--open` 与不带参数的**用户可见行为不同**，合成一个组件表达不了。
- `clipboard-panel` 去掉 `args`：否则"确保入口存在"会把完整面板弹出来。

**机器校验（不是靠自觉）**：

1. `lifecycle-owner` 命中 16 → **13**；两条清单条目因"现实中不再命中"被门禁**强制删除**（棘轮收缩）。
2. 新增门禁 **B5**：`CoreComponents` 常量 ↔ `components.json` 的 `name` **双向一致** ——
   C# 多出的名字 = 运行时 `unknown-component`；表里多出的名字 = 该组件**没有壳侧入口能到达**。
3. 冷启动验收读数见 [`../audits/2026-09-20-project-health-check.md`](../audits/2026-09-20-project-health-check.md) §10。

**未收敛（有意保留）**：`recovery` 与 `updater` **不能**由 core 管 —— 它们要在 core 坏掉/被替换时工作，
这属架构必需而非欠账；`--toggle-key` 见上文缺口表。

## 六、什么时候要改本表

- 任何一条 S4-4 / S5 / S6 / S7 / S8 收敛落地（删掉一个重复项后，本表必须同步）；
- `core/components.json` 的 tier/type 语义变化；
- 新增一门语言（C++ / Python / Node）接入 —— 那时矩阵的列要加，且**新列必须先证明自己不是所有者**。
