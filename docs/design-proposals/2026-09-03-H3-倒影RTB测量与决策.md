# H3 · 倒影 RTB 重建 Gen2 分配测量与决策

> Wave 2 资源卫生 · 先测量后改。2026-09-03。测量单测：`ReflectionRtbAllocationTests`（shell-dock-tests，STA）。

## 机制现状（源码确认）
`DockWindow.BuildReflection`（L1289-1387）：
- 每**每图标**新建 `RenderTargetBitmap`（按显示尺寸 iconSize×iconSize @96dpi，Pbgra32）→ Render（翻转）→ Freeze；
- 重建触发：`DependencyPropertyDescriptor.AddValueChanged(Image.SourceProperty)` 监听 Source 变化
  （异步图标加载完成即重建）+ 初次一次；视觉设置变更经 250ms 双层防抖全量重建（历史上防抖注释明言
  曾因反复建 RTB 触发渲染线程 OOM 崩溃）；
- 重建是**丢弃旧图重建新图**，无跨重建缓存。

## 测量结果（xunit STA，与生产同构路径：DrawingVisual + Scale(1,-1) + RTB）
一次全量 dock 重建 = 24 个图标 × 48px RTB（默认档）：

| 指标 | 实测 | 门槛 |
|---|---|---|
| 总分配 | **< 2MB**（24 × ≈9-15KB + WPF 包装开销） | < 2MB ✅ |
| Gen2 GC 次数 | **0** | 0 ✅ |

## 决策：**不引入倒影位图缓存**
理由：
1. 单次重建分配在百 KB 量级、零 Gen2 压力——不存在"Gen2 分配成为 GC 压力源"的机制证据；
2. 重建频率已被两层既有约束封顶：图标异步加载（低频一次性）+ 视觉设置 250ms 双层防抖
   （拖滑块合并），不是热路径；
3. 缓存键（图标源 × 显示尺寸 × 倾斜角 × 渐变参数）组合复杂，收益/复杂度比不划算。

## 顺手修掉的真泄漏（比分配问题严重得多）
`AddValueChanged` 把 handler 挂在**静态** DP 描述符上，会对元素（连同整个视觉子树）持强引用；
面板每次重建丢弃旧 `iconImage`，但 handler 不摘除即累积泄漏。修复：挂 `Unloaded` 自摘
`RemoveValueChanged`（面板重建时旧元素必然 Unloaded）。
