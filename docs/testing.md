# testing.md — 测试与取证策略

> 地位：一切测试相关规则的唯一真相源（MECHANISMS.md M9）。与 `scripts/verify-*.Tests.ps1` 的分工：本文件管「测什么、怎么算绿」，后者管「门禁单测的格式与覆盖要求」。

## 一、测试金字塔（自下而上）

1. 契约测试：内核三机制（服务图解析 / epoch 去重 / effect 逆序清理）的契约先行，先写测试再写实现（coding-standards 已冻结）。
2. 单元测试：每个包的公共类型必须有对应单测；测试工程命名 `*.Tests`。
3. 集成测试：跨包链路（loader→plugin→服务提供）P1 起覆盖。
4. 冒烟测试：每阶段结束必须能启动、能当外壳用（红线 R2 的判据）。

## 二、覆盖率政策

1. 内核包行覆盖率基线：**P1 定基线，棘轮只升不降**（与 README 棘轮同构）。
2. 覆盖率数据本身不是目标：改过核心逻辑却没有对应测试的 PR 可被打回（评审口径）。
3. 覆盖率豁免必须写明理由（对应 DSH coverage-exempt 思路），禁止成片豁免。

## 三、取证纪律（测试物证与门禁物证同一标准）

1. 禁 `--no-build`、禁拷贝预构建产物、取证前清 `bin`/`obj` 全量构建——对测试类物证同样适用。
2. 伪证整批作废（ADR-001 R4 已冻结）。

## 四、Flaky 处置

1. 连续三次全量重跑仍时红时绿的测试视为 flaky，必须修复或隔离（专用目录 + 决策记录说明），**禁止注释、禁止 Skip 了事**。
2. 隔离的 flaky 测试计入还债清单，只减不增。

## 五、性能基准

1. 启动时间 / 常驻内存基准纳入 CI（P2 落地 `verify-benchmark.ps1`）。
2. 相对基线回归超过 10% 即红；放宽阈值需决策记录。

## 机检状态（诚实标注）
