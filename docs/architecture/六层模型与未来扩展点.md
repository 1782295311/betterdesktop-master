# 六层模型与未来扩展点

> 状态：**现行**（2026-09-19 起）。本文是 core 重构计划的架构骨架，后续实现、门禁与评审都以本文为准。
> 上位总览：[architecture.md](../architecture.md)；完整计划：[2026-09-18-on-demand-core-architecture.md](../plans/2026-09-18-on-demand-core-architecture.md)；命名总表：[TERMINOLOGY.md](../TERMINOLOGY.md)；core 代码规范：[coding-standards-core-rust.md](../coding-standards-core-rust.md)；控制管道错误码：[error-codes.md](error-codes.md)。

## 一、本文要解决的问题

core 被定位为**未来十年的地基**（要承载 AI 管家、`bd-infer` 推理网关、`bd-world` 的 UE5 表面、GPU 仲裁、安全扫描）。地基的风险不在"现在能不能跑"，而在**现在没想清楚的事，未来要靠改 schema / 改架构来补**。所以本文只做一件事：把"现在不实现、但必须留位"的部分写清楚，让未来加东西时是**加表项**，不是**改结构**。

判断标准：本文里的每条规则，都要能回答"如果不写下来，未来谁会因为不知道它而踩坑"。

## 二、六层模型

```
⑥ 入口层     bdctl · bd-launcher · ShellDLL（explorer 内） · 托盘菜单 · 全局热键
⑤ 扩展层     system 扩展（AI 管家，经 core 调基础设施） · 普通扩展 · 技能扩展（out-of-proc）
④ 表面层     bd-shell（WPF 2D：菜单栏 / Dock / 搜索） · bd-world（UE5 3D） —— 用户可见的"脸"
③ 数据面     剪贴板历史引擎 · 索引引擎（Rust，按需拉起 + 空闲自退）
② 基础设施   bd-infer（统一推理网关：LLM + OCR + 翻译 + API 路由）
① 地基       core（Rust，唯一常驻）：托盘 · 热键 · 控制管道 · 监护 · 电源 · 安全 · GPU 仲裁 · 独占能力
```

| 层 | 职责 | 是否常驻 | 现状 |
|---|---|---|---|
| ① 地基 | 触发器 + 生命周期所有者 + 系统级独占资源 | **唯一常驻** | core 骨架已跑通（S1） |
| ② 基础设施 | 被多方消费的无 UI 能力（推理、扫描） | 按需 + 空闲自退 | 未实现，schema 已留位 |
| ③ 数据面 | 数据引擎（剪贴板历史、索引） | 按需 + 空闲自退 | 已实现（Rust 引擎） |
| ④ 表面 | 用户可见的桌面"脸" | 用户开启才跑 | shell / desktop 已实现；world 未实现 |
| ⑤ 扩展 | 功能件，经 core 控制管道协作 | 按需 | 部分已实现（capture 等） |
| ⑥ 入口 | 触发命令的一次性客户端 | 用完即退 | 已实现（CLI / Launcher / ShellDLL） |

## 三、依赖方向

**单向向下**：`⑥⑤ → ②①`，`④ → ②`（表面可调推理），`③ → ①`（数据面经管道受 core 监护）。

反向依赖一律禁止，具体三条硬规则：

1. **core（①）只认得组件表，不认得任何扩展的实现** —— core 里不得出现任何扩展的名字、类型或程序集引用。这是它能当地基的前提。
2. **扩展（⑤）不得依赖 core 内部符号，也不得自己拉起别的扩展** —— 要拉就发控制管道请求（`@ctl start <name>`），由 core 决定拉不拉、拉几个。
3. **表面（④）不得反向被基础设施依赖** —— `bd-infer` 不知道 `bd-world` 存在。

## 四、core 的定位与禁止清单

core **只做九件事**（职责编号稳定，勿重排）：

| # | 职责 | 状态 |
|---|---|---|
| A | 托盘图标（`Shell_NotifyIconW` + 隐藏顶层窗口） | S1 已实现 |
| B | 全局热键（含"必须活过壳退出"的全部热键） | S4 |
| C | 控制管道（`BetterDesktop.MenuCmd` 服务端 + `@ctl` 形态） | S2 |
| D | 监护器（reconcile + 退避 + degraded + 计划任务） | S3 |
| E | ShellMenu 快照**触发**重建（不写内容） | S6 |
| F | 独占能力（任务栏外观 / 桌面图标钩子） | S4 |
| G | **电源事件处理**（`WM_POWERBROADCAST`） | S3.5 |
| H | GPU 仲裁（GPU 用户表；策略留位） | S5.5 |
| I | 安全基线（管道 ACL / 调用方校验 / 路径校验） | S2.5 |

**禁止清单**（core 一旦越界就会变成"第二个 host"，那时再拆代价极高）：

- 不得加载任何 UI 插件（dock / menu-bar / start-menu / island / quick-note / hotkeys-panel）；
- 不得渲染任何面板；
- 不得持有任何业务状态（不缓存应用列表、不存剪贴板内容、不存最近项、不存索引）；
- 不得读业务数据文件（除 `settings.json` 的扁平键、`components.json`、留痕 flag）；
- 不得引用任何 C# 程序集或业务包。

## 五、组件表 schema 的层级语义

`core/components.json` 是 core 的唯一业务数据。字段全貌与默认值见该文件内的 `_comment`，此处只写**语义与判据**。

### 5.1 `tier` —— 层级归属，决定监护规则

| tier | 监护规则 |
|---|---|
| `foundation` | 常驻，永不缺席、永不停（`auto_start` 恒真、`must_stop` 恒假） |
| `infrastructure` | 按需（有消费者时拉起，空闲自退） |
| `surface` | 用户开启才跑（`gate` 主控，gate 关**必须停**） |
| `extension` | 按需（收到 `start` 才拉） |
| `system-extension` | 按需，且可请 core 代为拉起其它层（**自己不 `Process.Start`**） |

**`surface` 的判定口径**（消除"桌面算不算 surface"这类反复讨论）：`surface` = **构成用户感知到的「桌面这张脸」**的组件，即 `shell`、`desktop`、未来的 `world`。判据一句话：**关掉它，用户会问"我的桌面怎么变了"** → surface；**关掉它，用户只是少了个能打开的工具** → extension。按此口径，设置中心、剪贴板面板、通知面板都**不是** surface，而是 `extension` + `type=panel`。

### 5.2 `type` —— 形态

`process`（常驻/按需进程） / `tool`（一次性工具，跑完即退，不守护） / `panel`（UI 面板，按需拉起）。

`tool` 的预留用途：未来的安全扫描器 `scan-file` —— AI 管家发 `@ctl run scan-file <path>`，core 拉起一次性 `BetterDesktop.Scanner.exe`，完即退，**不进监护名单**。

### 5.3 `power` —— 电源策略

`onSuspend`：`freeze`（默认，什么都不做，唤醒后进程仍是活的） / `stop`（主动停止） / `notify`（只通知）。

`onResume` 取值与适用层：

| 取值 | 语义 | 适用层 |
|---|---|---|
| `reconcile`（默认） | 按差集 reconcile：**先探活，只补真缺的** | `extension` |
| **`probe-and-reinit`** | **先探测健康，不健康才重新初始化** | `surface` |
| `reinit` | 无条件重建外部资源（GPU 上下文 / 句柄 / 连接） | `infrastructure` |
| `restart` | 强制重启（最后手段） | 兜底 |
| `notify` | 只通知，由组件自理 | 特例 |

`keepAwake`：`false`（默认） / `"user-triggered"`（仅用户显式触发的长任务期间，**且必须带超时**）。**`true` 与 `"always"` 会被 schema 拒绝** —— 这是"core 让系统睡不着"这类 bug 的直接防线。

## 六、电源：唤醒时序与健康探测

### 6.1 为什么 `reconcile` 不够

`reconcile` 只能回答"**进程在不在**"，回答不了"**它还能不能用**"。对 Surface 层不够：

| 场景 | 进程状态 | 实际可用性 |
|---|---|---|
| 睡眠唤醒后 DWM 重建 | WPF 进程活着 | 窗口可能花屏 / Z-order 错 |
| 唤醒后 D3D12 设备丢失 | UE5 进程活着 | 渲染不出来 |
| explorer 重启 | ShellDLL 宿主进程活着 | 右键菜单不工作（钩子失效） |

故 `probe-and-reinit` = 经控制管道 `@ctl health <name>` **询问组件自报健康**；无应答 / 超时 / 返回不健康 → 按 `reinit` 处理。
**探针的具体实现由组件自己提供** —— core 只知道"问"，不判断 WPF 窗口或 D3D 设备的细节。这正是"core 只做触发器"的分层依据；反过来，如果 core 要自己判断窗口健康，它就不得不懂每种 UI 技术，地基立刻变成耦合中心。

**纪律（由 schema 校验 + 启动警告保证）**：声明 `tier=surface` 且 `desired=running` 的条目**必须显式写 `onResume`**。留空（= 默认 `reconcile`）会导致"唤醒后窗口花屏却无人重建"被静默放过。

### 6.2 唤醒时序（顺序红线）

```
PBT_APMRESUMEAUTOMATIC / PBT_APMRESUMESUSPEND 到达
  ⓪ 先重置所有计时器   ← 顺序不可颠倒
  ① 重新枚举子进程（部分可能被系统杀掉）
  ② 重新注册热键（若丢失）
  ③ 重建托盘图标（若丢失 / explorer 重启过）
  ④ 重建管道服务端实例（旧连接可能已断）
  ⑤ 重新获取独占能力（任务栏外观 / 桌面图标钩子）
  ⑥ 按各组件 power.onResume 分派
  ⑦ 对 probe-and-reinit 的组件：先探健康，不健康才重建
```

**为什么 ⓪ 必须在最前**：睡眠期间所有计时器都在"冻结"。唤醒瞬间它们会**同时**到期 → 监护循环可能在"还没有实际探活结果"时就并发发起多轮拉起；更糟的是退避计时器归零会让 `degraded` 熔断被误判为"已冷却"，于是对刚失败过的组件立刻重试。先归零/重建计时器，再探活、再 reconcile，才能保证"一次唤醒 = 一次动作"。

### 6.3 睡眠前的动作

`PBT_APMSUSPEND`：暂停监护循环（避免把冻结误判为崩溃）、持久化 core 状态（desired/actual 快照）、释放可选资源。

## 七、运行时资产命名表

> 本文只登记**运行时资产**（进程 / 管道 / 留痕 / 日志 / 命令 / 事件 / 配置键）；术语、目录↔命名空间↔程序集映射、禁用术语见 [TERMINOLOGY.md](../TERMINOLOGY.md)。
> 之所以不把此表并入 TERMINOLOGY.md：那份已有字数预算且顶格，而本表与架构强耦合（分层/监护规则同源）。**新增运行时资产时以本表为准**，避免同一概念出现第三个名字。

| 类别 | 规则 | 既有实例 |
|---|---|---|
| 可执行体 | `BetterDesktop.<Name>.exe`；`Name` 用 PascalCase 单词 | `BetterDesktop.Core.exe`、`BetterDesktop.Host.exe`、`BetterDesktop.DesktopControl.exe` |
| 命名管道 | `BetterDesktop.<Domain>` | `BetterDesktop.MenuCmd`、`BetterDesktop.DesktopCmd`、`BetterDesktop.Clipboard.Engine` |
| 命名互斥量 | `Local\BetterDesktop.<Name>.SingleInstance-<guid>` | `Local\BetterDesktop.Core.SingleInstance-3c1f0a74-…` |
| 控制命令词 | 小写 kebab：`<verb>` 或 `<verb> <component>` | `status` / `start desktop` / `set <key> <value>` |
| 配置键 | 扁平点分：`<域>.<子域>.<键>`；域限 `components` / `extensions` / `desktop` / `hotkeys-panel` | `components.desktop`、`extensions.index.enabled` |
| 留痕 flag | `%LOCALAPPDATA%\BetterDesktop\<名>.flag` | `host-stopped.flag`、`shellmenu-unregistered.flag` |
| 日志 | `%LOCALAPPDATA%\BetterDesktop\logs\<进程名>-yyyyMMdd.log` | `core-yyyyMMdd.log`、`tray-yyyyMMdd.log` |
| 计划任务 | `BetterDesktop <Name>` | `BetterDesktop Core Ensure` |
| 组件表字段 | 小驼峰（`keepAwake`）或全小写单词（`name` / `tier`） | 见 `core/components.json` |

## 九、电源红线（禁止事项）

以下为**硬性禁止**，由门禁与代码评审共同保证：

1. 禁止在 core 启动时调用 `SetThreadExecutionState`。
2. 禁止无条件持有 `PowerSetRequest`（`keepAwake` 的 `true` / `"always"` 已被 schema 拒绝）。
3. 禁止计划任务配 `WakeToRun=true`（不得唤醒机器）。
4. 禁止计划任务配 `StartWhenAvailable=true`（睡眠错过后不补跑 —— core 醒来自己 reconcile）。
5. 禁止子进程持有 `ES_SYSTEM_REQUIRED`（除非用户显式触发且带超时）。
6. 禁止在 `WM_POWERBROADCAST` 处理之外做电源假设（例如"计时器一定还在走"）。

**验收判据**：`powercfg /requests` 在 core 运行时**必须为空**。
