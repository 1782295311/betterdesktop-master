## 一、背景

P0 已交付治理框架与七道门禁。P1 目标是内核落地。三件悬而未决必须先裁定：其一，依赖选型（交接实测骨架曾引入 `Microsoft.Extensions.DependencyInjection.Abstractions`，已被移除待裁定）；其二，服务生命周期与事件契约没有成文；其三，交接实测产出的契约接口（IContext/IPlugin/IPluginHandle/IEventBus/PluginState/IEffectManager）需要裁定保留、修改或废弃。Cordis 真源的三机制——服务图、依赖驱动重载（epoch 去重）、effect 逆序并行清理——是 P1 契约测试的三块基石。

## 二、决策

### D1 · 内核最小 API 面（冻结）

| 类型 | 职责 | 裁定 |
|---|---|---|
| `IContext` | 服务图与插件生命周期容器：显式 `Get<T>()`（无透明代理）、`Provide<T>()`（变更通知依赖者）、`Extend()`（父链继承）、`Plugin()`（一切皆插件的唯一通道）、`Effect()`（托管清理）、`Events`、`Logger` | 保留并调整（原骨架同名接口扩展） |
| `IPlugin` | `Name` / `Inject`（必需依赖类型）/ `LoadAsync(ctx)` / `UnloadAsync()` | 保留 |
| `IPluginHandle` | Fiber 对应物：状态机 Pending→Loading→Active→Failed→Unloading→Disposed；`AwaitAsync` / `RestartAsync` / `DisposeAsync` | 保留（原骨架无此类型，新增） |
| `IEventBus` | 事件名「域/动作」+ 强类型载荷 + 五种分发（emit/parallel/serial/bail/waterfall） | 重设计（原骨架泛型签名改为「事件名+载荷」模型） |
| `CapabilityAttribute` | 能力元数据声明位（M16 前置）：id/描述/权限等级/可撤销 | 新增 |
| `IEffectManager` | 独立清理器管理接口 | **废弃**——effect 归于 `IContext.Effect()`，与 Cordis 原语一致 |

**明确不在 v1**（P2 范畴，避免大爆炸）：HMR、进程外隔离、intercept 配置拦截合并、isolate 完整实现、透明代理。

### D2 · 依赖选型（裁定）

1. `kernel/kernel` **零第三方运行时依赖**（纯 BCL）。**不引入 MS DI**：MS DI 无 provide 变更通知与依赖驱动重载语义，套壳只会形成第二套机制（老仓「多套并存」失败模式的同构风险）；服务图自实现。
2. 日志：内核自带 `IKernelLogger` 最小实现（sink 注入），不引 `Microsoft.Extensions.Logging`；P2 宿主接文件管道。
3. 测试依赖（xUnit 等）仅限 `*-tests` 包。

### D3 · 服务生命周期（裁定）

| 作用域 | 语义 | v1 状态 |
|---|---|---|
| root | 宿主级服务，随根上下文存活 | ✅ 实现 |
| plugin | 插件加载期提供，随插件 fiber 卸载（effect 托管） | ✅ 实现（Provide 全局可见——角色替换语义的前提） |
| transient | 每次解析新建 | v1 不实现（记录为已知限制） |

### D4 · 事件契约（裁定）

1. 跨插件/跨包通信一律走内核 `IEventBus`；**禁止跨程序集裸 C# `event`**（coding-standards 禁止清单第 3 条自此落地）。
2. 事件名约定 `<域>/<动作>`（如 `shell/theme-changed`）；载荷强类型。
3. 分发五种：emit（并发广播）/ parallel / serial / bail（首个非默认值短路）/ waterfall（同类型顺序折叠）。
4. 单监听器异常隔离：不阻断其余监听器，异常入内核日志。

### D5 · 命名与分层（裁定）

1. 命名空间：`BetterDesktop.Kernel.Contracts`（插件消费面，稳定 API）与 `BetterDesktop.Kernel.Core`（实现，不承诺稳定）。
2. 内核不引用 WPF；UI 封送在 P2 由 shell 层 Dispatcher 服务实现。
3. 能力元数据：P1 仅声明位（`CapabilityAttribute`），目录聚合与权限执行 P2（ai-control.md 验收清单）。

## 三、后果

**接受的代价**：自实现服务图（放弃 MS DI 生态）；v1 无 HMR / 拦截合并 / 进程外 / transient；事件总线载荷类型不匹配属调用方契约错误（抛 `InvalidCastException`）。

**获得的收益**：Cordis 语义完整（通知、重载、托管清理）；内核零依赖可审计；ABI 面小（五接口一特性类）；角色替换（pluginization）与能力目录（ai-control）都有真实落点。

**P1 验收判据**：内核三机制契约测试绿并有物证；`dotnet format` 门禁通电（含红证）；构建 0 错误 0 警告（`TreatWarningsAsErrors`）。

## 四、被否决的备选方案

| 方案 | 否决理由 |
|---|---|
| A. 引入 MS DI 套壳 | 无 provide 通知 / 依赖重载语义；双容器即腐化 |
| B. DispatchProxy 透明代理 | 性能与调试成本高；显式 `Get<T>` 已足够（coding-standards 禁止清单 2） |
| C. v1 就实现 HMR / 进程外 / 拦截合并 | P2 范畴；一次大爆炸违反 ADR-001 R2「每阶段可运行」 |
| D. 引 Microsoft.Extensions.Logging | 内核零依赖原则；v1 自实现 Logger，P2 宿主决定管道 |
| E. 保留 IEffectManager 独立接口 | effect 是 Context 原语（Cordis `ctx.effect`），拆成独立服务是多此一举 |
