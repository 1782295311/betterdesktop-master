# Post-mortem 制度

> 事故是免费的设计课。每一次 P0 级事故必须产出一篇事后分析，否则视为事故未闭环。

## 写作判据与定位

事后分析记录的是：一个 bug 出现在了不该出现的地方（真实用户、已合并的 PR、已发布的版本），值得关注的是**为什么流程放过了它**，而不仅仅是那一行修复。它回答：什么坏了、机制是什么、为什么每道安全网都没拦住、为此新增了哪些具体防护措施。

每篇以一段**执行摘要**开头——让忙碌读者在三十秒内吸收要点：什么坏了、用直白的话说根因、为什么逃逸、可长期沿用的教训——之后才是「时间线与症状 / Root cause / Guardrails / 复盘点」各节。**必须链接**本事故推动建立的防护措施（测试、AGENTS.md 规则、ADR、门禁）。

## 触发条件（满足任一即强制成文）

- 数据丢失或不可恢复的配置损坏
- 门禁被绕过 / 伪证被采信 / 基线被悄悄放宽
- 主干不可构建窗口突破 ADR-001 红线 R2 的 1 个工作日
- 任何「同一根因复发第二次」的故障

## 格式

- 文件：`docs/postmortem/NNNN-title.md`（NNNN 四位序号，自 0001 递增）
- 必需小节：`## Executive summary` / `## 时间线与症状` / `## Root cause` / `## Guardrails`（新增了哪条门禁或流程、物证在哪）/ `## 复盘点`
- 索引：登记进本文件下方表格（漏登记由未来门禁 `verify-postmortem-index` 拦截）
