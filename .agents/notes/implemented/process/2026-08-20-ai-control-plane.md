# Agent Note: AI 控制面规范落地——能力目录、分级授权、人在环、可审计与防失控

Status: implemented — 2026-08-20，用户提出「还应留给 AI 控制程序功能的入口」

## Problem

用户要求为 AI 预留控制程序功能的入口。老仓 Companion（桌宠）的失败模式必须避免：AI 与功能之间是硬绑定调用、无权限模型、无审计——AI 一旦出问题，用户既不知道发生了什么，也无法撤销或禁用。同时 DSH 的 tool catalog 实践证明了正确形态：能力由机器生成目录、Agent 按目录受限调用。若不现在立规则，P1 内核可能不留能力元数据的位置，后期再补就是结构性返工。

## Decision

1. 新增 `docs/ai-control.md` 并登记 M16，六节内容：
   - 能力目录唯一注册处：复用 M5 插件/服务通道 + 元数据，不建第二套注册表；未登记不可见不可调（fail-closed）；P2 起 gen --check。
   - 入口三档：内核级 `IAiControlPlane` / 本地命令 / 回环 MCP server（只绑 127.0.0.1 + 会话令牌，禁止默认对外）。
   - 权限分级四级（L0 只读 / L1 常规 / L2 敏感确认 / L3 高危禁止）+ 人在环确认 + 与 security.md 同级约束。
   - 可观测可审计可撤销：审计日志走 runtime-health 单管道；可撤销能力预留 Undo 语义；AI 活动在状态中心可见（防「鬼手」）。
   - 防失控：速率限制与配额、禁递归回调、AI 控制面整体可停用且停用后 shell 全功能可用（AI 永不成为依赖）。
   - 验收判据：目录/越级/审计/停用四组演练物证（P2/P3）。
2. 联动：`docs/architecture.md` 内核要点表补「AI 控制面」一行；TERMINOLOGY 增补能力目录 / 控制面 / 人在环 / 审计日志术语。
3. 明确对 ADR-002 的约束：内核服务与命令模型必须预留能力元数据位（描述/参数 schema/权限等级），否则 M16 无法落地。

## Alternatives considered

- 不给 AI 入口：否决——用户明确要求，且 AI 生态是社区型产品的第二增长曲线；不给入口的代价是社区各自 hack 出无权限模型的野路子。
- AI 走与人类完全相同的最高权限：否决——等于没有权限模型，老仓 Companion 已实证其风险。
- 为 AI 另建第二套能力注册表：否决——违反 M5「一切皆插件」单一通道；能力 = 服务 + 元数据是唯一形态。
- 现在就实现 MCP server：否决——无内核可挂；规则先于代码，P2 落地并取红证。

## Consequences

- ADR-002 的验收清单新增一条：内核能力模型必须支持元数据登记（M16 前置条件）。
- P2/P3 验收新增四组演练物证，与替换/崩溃注入演练并列。
- 社区第三方 Agent 获得明确接入契约：读能力目录、按权限调用、全程留痕。
