# Agent Note: core 的黑窗口与「主动退出不许拉回来」（崩溃 vs 正常退出）

Status: implemented — 2026-09-20，`core` 单测 211/211 绿（新增 7 条），release 已构建，三项真机验证通过

## Problem

两个真机症状（用户报告 + 截图）：

1. core 每次启动都伴随一个**黑色控制台窗口**，标题是 `…\app\2026.09.20.1350\betterdesktop-core.exe`；**关掉那个窗口，core 也一起死**。
2. 从托盘主动退出后，core 在 5 分钟内被计划任务拉回来。用户的要求是："主动退出不应该再被拉回来，所以要做好崩溃和正常退出的区别"。

取证：

1. 读 PE 可选头的 `Subsystem` 字段（`Offsets: pe + 24 + 0x44`）：部署中的 `app\2026.09.20.1350\betterdesktop-core.exe` = **3（Windows Console）**，新构建改后 = 2（Windows GUI）。console 子系统的进程在**没有控制台的上下文**里启动（任务计划、`Start-Process`）时，Windows 会为它**新分配一个控制台** ⇒ 黑窗口，标题默认就是 exe 全路径；而关闭该窗口 = 向进程发 `CTRL_CLOSE_EVENT` ⇒ 默认处理终止进程。这正是截图的成因，也解释了"关黑窗口 core 就死"。
2. 复活引擎是计划任务 `BetterDesktop Core Ensure`（PT5M），已在 `2026-09-20-task-ownership.md` 取证。而兜底任务与"用户显式启动"跑的是**同一个可执行体、同一份命令行**，core 当时无法区分二者 —— 于是"崩溃要拉回"与"主动退出不许拉回"这两条不可能同时成立。

## Decision

两件事各用一个最小但完整的机制。

**一、GUI 子系统**：`core/src/main.rs` 加 `#![windows_subsystem = "windows"]`。core 从不写 stdout/stderr（`log.rs` 只落盘，全仓 `println!`/`eprintln!` 命中数为 0），所以零输出损失；子进程侧也不会因此冒出新窗口 —— `process.rs` 两处 `CreateProcessW` 都已带 `CREATE_NO_WINDOW`（schtasks / CLI 不会因为父进程没有控制台而新开一个）。

**二、停止语义**（写入 `task.rs` 模块头，与 `components.json` 的 `stopFlag` 同构）：

- **正常退出** = 写 `%LOCALAPPDATA%\BetterDesktop\core-stopped.flag` + **删掉兜底任务**；顺序是"先写标记、再删任务"（同 `main::stop_component` 的纪律：先做几乎不会失败的那一步）。两道防线各有分工：删任务是**意图**（兜底不该再存在），标记是**保险**（万一删除失败，任务再敲门时 core 自己会拒绝）。
- **崩溃** = 什么都不留（没有任何代码去写它）⇒ 兜底照常工作。这就是用户要的"崩溃与正常退出的区别"。
- 反向：**任何非兜底发起的启动都算"用户要它跑"** ⇒ 清标记。为此兜底任务的动作**必须带上 `--from-task`**（新常量 `task::LAUNCH_MARKER`，任务定义与 argv 判定共用同一个字面量）。这个参数**是信息，不是便利开关** —— 它与模块头原先"动作不得带参数"那条决定相反，反转的理由记在模块头「停止语义」与这里。
- 清标记的位置在**单实例互斥量之前**：它表达的是**意图**，与"本次实例有没有抢到锁"无关。真机验证时先放在锁之后，结果"已有一份在跑"时意图被丢掉（日志只有 `another core instance is running; exiting`）—— 这是验证才发现的。
- `classify` 一并比对 `<Arguments>`：旧定义（无标记）判 `TaskState::Stale` ⇒ 下次 core 启动时自动 `Repaired`，**不需要手工迁移**。
- 管道动词同步：`task register` → `task::arm()`（先解除停止态再 `ensure()`，否则会被**正确地**拒绝，表现为"命令成功了、任务却没回来"）；`task unregister` → `task::stop()`（否则撤掉只是暂时的，下次 core 启动装回来 = "我删了它又回来了"）。
- 托盘菜单文案由「退出 BetterDesktop Core」改为「退出 BetterDesktop Core（不再自动拉起）」。

## Alternatives considered

- **只修子系统、不修退出语义**：否。用户报的是两个独立缺陷。
- **用"父进程是不是 svchost"来判断本次是否来自兜底**：否。宿主会变（任务计划的宿主进程不保证），而"来源"必须是**显式、可 diff** 的信息 —— 写在任务定义的 `<Arguments>` 里比猜进程树可靠，且它顺带给了自动迁移一个落点。
- **停标记只挡"注册兜底"、不删任务**：否。任务会继续每 5 分钟敲一次门、每次都被拒；一条注定无用的系统级引用留在用户机器上，`schtasks /query` 还会把它显示成"健康"。删掉才与"用户说不要了"这个事实一致。
- **停标记只删任务、不写标记**：否。删任务依赖 `schtasks`，是两步里更可能失败的一步；一旦失败，用户看到的就是"我退了它又回来了"，而没有任何东西能解释原因。
- **每次启动都清标记（不区分来源）**：否。那等于兜底每次把用户的停止决定自我推翻，正是本次要修的故障。
- **让启动器 / CLI / 安装器各自清标记**：否。5 个启动点各记一次，漏一个就变成"用户点了启动却没反应"的静默故障。改成"非兜底发起 ⇒ core 自己清"，写入者一个、读取者一个。
- **同时给 GUI 子系统补一个 panic hook**：本批不做。core 生产路径禁 `unwrap`/`expect`，崩溃由兜底拉起、启动日志可看出断点；精确归因需要 WER 或专门的 hook，属独立课题。

## Consequences

- 用户侧：黑窗口消失；托盘「退出」之后 core 不会被自动拉起，除非用户显式启动（启动器 / CLI / 安装器 / 双击）。
- 迁移自动完成：旧任务定义（无 `<Arguments>`）在下次 core 启动时被判 `Stale` 并 `Repaired` 成新定义。
- **已知边界（有意接受）**：退出**不**动 `HKCU\...\Run` 的「开机自启」—— 那是用户在托盘菜单里看得见、能自己关的显式设置。所以开了自启的用户退出后，**下次开机**仍会起来；那是设置本身的语义，不是被兜底"拉回"。
- **未覆盖的入口**：`recovery --clean-autostart` 按名字删任务与 Run 值，但**不写**停止标记（它是零依赖的应急程序，不扩跨进程字面量清单）。它跑完会终止所有 BetterDesktop 进程，所以当场没有"被拉回"的窗口；此后任何一次显式启动会把兜底装回来 —— 与"应急恢复"的语义一致。
- 真机验证（可复现，三项全过）：① 读 PE 可选头 `Subsystem`；② 把两个产物各拷一份到 `%TEMP%` 并**改成不同文件名**后启动，枚举顶层窗口标题（控制台窗口标题 = 被启动 exe 全路径）—— 旧产物**命中**（阳性对照成立）、新产物**无命中**；③ 创建 `core-stopped.flag` 后分别以 `--from-task` 与裸方式启动：日志依次出现 `launched by the fallback task, but core is STOPPED by the user …` 与 `explicit start: cleared 'core-stopped.flag'`，标记在两种情形下的去留均符合预期。验证全程未停正在运行的 core、未改计划任务。
- 单测：211/211（新增 7：标记字面量、动作带标记、`classify` 对缺失/外来参数的两种拒绝、argv 判定正反、停止标记名、只读探测）。停止语义本身依赖真实文件与 `schtasks`，按"单测不得产生副作用"的纪律**不在单测里制造停止态**，由上面的真机验证覆盖。
- 未做（需要用户决定时机）：把新构建**部署**到运行中的 core —— 部署前，用户机器上跑着的仍是 console 子系统那份，黑窗口与"退了又回来"都还在。部署后旧任务定义会被自动迁移。
